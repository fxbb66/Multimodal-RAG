## 1. 项目定位与总体架构

### 1.1 做的是什么

面向"上海迪士尼度假区客服"场景的**多模态检索增强问答（RAG）系统**：把 69 份异构企业资料（Word/PPT/PDF/价格图片）建成可问答的知识库，用户用自然语言提问，系统经过**意图识别 → 混合召回 → Rerank → 多样性后处理 → 受约束生成**，给出带来源引用的流式回答；问题过于模糊时先澄清，多意图问题自动拆分。

个人项目，独立完成从数据解析、索引构建、检索调优、评估体系到 Flask 服务部署的完整闭环。

### 1.3 关键设计取舍（一句话版）

| 选择 | 放弃的方案 | 理由 |
|---|---|---|
| 结构感知切片 | 定长 800 硬切 | 句子不被切断；标题/表格/章节结构是免费的高精度信号 |
| 三类文档统一成 block 流 | 每个格式各写一套切片逻辑 | Chunker 只认 block，格式差异在解析器内消化 |
| BM25 字符 bigram | jieba 分词 BM25 | 中文短查询友好、零依赖、无分词错误传导 |
| IndexFlatIP + L2 归一化 | L2 距离索引 | 内积即余弦；481 条向量暴力检索毫秒级，无需 IVF/HNSW |
| 图片 OCR+caption 文本入**同一**个库 | 独立图片库/以图搜图 | 文字问题（"邮轮价格"）可直接召回到图片；一套检索链复用 |
| RRF 等权融合 | 分数加权 | 两路分数量纲不同不可比；位次融合无需标定尺度 |
| 表格 Markdown 整块保留 | 拍平成段落 | 行列结构对票价/时刻表类问题是必要语义 |
| 规则门 + LLM 意图双轨 | 纯 LLM 意图 | "多少钱"类 LLM 曾稳定误判；确定性规则零成本兜住 |

## 3. 阶段 0：旧格式转换（0-转换旧格式.ps1）

旧版 `.doc/.ppt` python-docx/python-pptx 无法读取，用 Windows 本机 Word/PowerPoint COM 自动化批量转成 `.docx/.pptx`，并写 `converted/manifest.json` 记录映射。

这一步踩的环境坑（都发生在项目第一天）：

1. **全局 Python 权限**：`C:/Python313` 受保护目录装包失败 → 全项目硬性规定一律走 `.venv\Scripts\python.exe`；
2. **PowerShell 5.1 编码**：无 BOM 的 UTF-8 中文脚本被按 GBK 解析而乱码 → 必须用 PowerShell 7 执行；
3. **盘符大小写**：COM 写的 manifest 里是大写 `D:`，`os.walk` 返回小写 `d:`，字典键全部对不上 → `os.path.normcase` 归一化后再比对；
4. **FAISS 中文路径**：`faiss.read_index/write_index` 底层走 C 库 `fopen`，不支持非 ASCII 路径 → 统一经 ASCII 临时目录中转（[lib/retriever.py](../lib/retriever.py) 的 `ascii_faiss_path`，构建侧写临时文件再 `shutil.move`）；
5. 后台进程：`Start-Process -WindowStyle Hidden` 起的服务间歇 502，改为 venv python 直接后台运行才稳定。

## 4. 阶段 1：结构感知解析与切片

> 代码：[1-parse_and_chunk.py](../1-parse_and_chunk.py)（约 1300 行，全项目最复杂的单文件）

### 4.1 五条总原则（先于一切具体规则）

1. **语义边界优先，800 字只是预算不是刀口**：以段落为最小聚合单位，绝不在句子中间硬切；只有单个段落本身超长才启用递归切分；
2. **结构信息必须保留并喂给检索**：标题路径（面包屑）拼进 embedding 正文首行；表格整块保留 Markdown；
3. **内容降级而不是删除**：伪表格/巨型格/失衡表尽量转成段落保住文字，唯一例外是 PPT CHART 形状（其文字纯是轴刻度/数据点，无阅读价值）；
4. **不可逆动作放最后**：chunk id 在去重、合并、过滤全部完成后才顺序分配；
5. **启发式规则先全库标定再上线**：每条规则都必须能列出"全库命中清单 + 误伤清单 + 阈值依据"。

参数常量（[1-parse_and_chunk.py:27](../1-parse_and_chunk.py#L27)）：

```
CHUNK_SIZE=800      CHUNK_OVERLAP=120
SHORT_MERGE_LEN=100  MAX_MERGED_LEN=1200   MIN_CHUNK=8
```

### 4.2 统一中间表示：block 流

三种格式解析后都输出同一种 block 序列，Chunker 只认 block：

| block kind | 含义 | 携带字段 | 对切片器的作用 |
|---|---|---|---|
| `h` | 标题 | level(1–9)、text | 维护标题栈/面包屑，自身不产生 chunk |
| `p` | 普通段落 | text | 进缓冲聚合；单段超长才 hard_split |
| `table` | Markdown 整块表 | text | 强制 flush 后独立成块，永不与正文合并 |
| `section` | PDF 语义章节 | text | flush + **零重叠**换章 + 弹栈到 level<2 |
| `boundary` | PPT 换幻灯片 | — | flush + 标题栈重置为文档名 |

### 4.3 DOCX 解析（parse_doctx，[:268](../1-parse_and_chunk.py#L268)）

- 按 `doc.element.body.iterchildren()` **沿物理顺序**遍历，用 element→对象的两个 map 区分段落与表格。不能分别取 `doc.paragraphs` / `doc.tables`——那样会丢掉表格与段落的相对顺序；
- 标题级别三级兜底：样式名含 `Heading/标题` → 正则取数字 → 读 `outlineLvl+1` → 都没有按正文。

### 4.4 PPTX 解析（[:361](../1-parse_and_chunk.py#L361)）

- 每张幻灯片固定产出 `boundary + h1("幻灯片N：标题") + 内容 + 演讲者备注`，保证**一张幻灯片一个 chunk**（超长再递归切）；
- GROUP 组合形状递归展开；标题形状显式跳过避免标题文字重复进正文；
- **CHART 形状整体跳过**（柱状图/饼图是 `MSO_SHAPE_TYPE.CHART`，提取出来的文字只有"212.99/轴刻度"这类噪声）；表格再过一遍 `_is_chart_data_table`（列数 ≥6 或数字单元格占比 >40%）双保险，拦住图表内嵌的"编辑数据"工作表；
- `join_vertical_text`：连续单行单字（"巍\n峨\n耸\n立"）纵向文本框合并，但保留 `·•◆■▪` 项目符号；独立纯数字行（刻度）丢弃。

**实测收益**：464 → 444 chunk，纯数字噪声块 38 → 2。

### 4.5 PDF 解析（[:679](../1-parse_and_chunk.py#L679)，四件事）

**① 预扫描整本建章节词典**（`_collect_pdf_sections`）
- 来源一：页眉文档名块（y0<45）之后、高度 45–140 区间内的单行短标题（探险世界/住宿/乐园服务），收集时跳过表格 bbox 防表头污染；
- 来源二：目录页按 `/ ／ •` 和多空格切 2–10 字条目；数字开头的价格项、"目录/content"本身、带句读标点的不收。

**② 逐页分流**：去空白文本 ≥20 字走文本通道；否则判定疑似扫描页——且页内确有图像/绘图才调 OCR（dpi=200，RapidOCR 单例，按"normcase 绝对路径→页码"缓存到 `ocr_cache.json`，tmp+replace 原子写）。

**③ 表格与正文合流**：
- `find_tables` 检出的表先按取整 bbox 去重；
- `_is_prose_mistable`：存在 >60 字且含 `。；` 的单元格 → 判双栏正文误判（全库仅香港攻略 p15 命中；真表皇岗专线最长格 186 字但只有冒号逗号，零误命中）；
- 表格外文本块按"中心点落入表 bbox 且面积重叠 >30% 则跳过"排除后，与表块**统一按 y0 纵向排序**恢复阅读顺序；
- 被判伪表/误判的表根本不进表格通道，其 bbox 内文字自动回流普通文本块——**同一份内容只保留一条通道**，避免重复入库。

**④ 噪声与章节分类**（`_classify_pdf_text`）：
- 页脚："返回目录我要纠错"，或坐标模式下 y0 > 页高 88% 的纯数字页码；无坐标拼接段按行剥页码；
- 页眉：y0<45 且等于文档名（含前 4 字 name_key 的近似匹配）；
- 章节标题：词典命中直接通过；否则形态启发——3–10 字、纯中英数字（允许·）、含中文、无标点、不含虚词表（"的了在于和与"），防止把半句正文当标题；
- 每页补一个 level=9 的 h"第N页"：页码进入面包屑但不干扰章节栈。

### 4.6 Chunker 状态机：block 流如何变成 chunk（[:849](../1-parse_and_chunk.py#L849)）

核心数据结构是"**标题栈 + 累加缓冲**"的单遍状态机：

- **面包屑**：栈内标题用 ` > ` 拼接（如 `香港迪士尼乐园旅游攻略 > 第12页 > 探险世界`），emit 时拼成 `面包屑\n正文` 作为 content——标题语义随每块一起进 embedding，显著提升主题相关性；
- **段落聚合**：段落不断 append 进 buf，`buf_len + 新段 > 800` 才 flush；
- **重叠不是切 120 字**：取上一块正文尾部 120 字，在窗口内找最后一个 `。！；\n`，**从标点之后**开始作为下一块前缀，避免重复半句；
- **章节边界零重叠**：遇 section 先 flush 再显式清空 buf——跨章带 overlap 会串味；
- **表格不进缓冲**：先 flush 正文，再逐片 emit；表格与正文、表格与表格之间永不合并；
- **PPT boundary**：flush 后栈直接重置为文档名（幻灯片标题之间没有层级继承）；
- **超长段落 hard_split**（[:781](../1-parse_and_chunk.py#L781)）：分隔符按语义强度降级 `\n → 。！？； → ". " → ，、 → 空格 → 字符硬切`，在 `[0.55×800, 800]` 窗口内找**最后一个**分隔符下刀，保证每片尽量长且边界自然；
- **超长表 split_long_table**（[:814](../1-parse_and_chunk.py#L814)）：超 800 字才切，**每组都重复表头两行**（没表头的数据行无法独立阅读）；组内超长行扣掉表头预算后再 hard_split。

### 4.7 表格统一管线（坑最密集的地方）

所有来源的表格都走 `sanitize_table_rows → 四元组判定 → 分流`。

**第一步：单元格级清洗**
- `\xa0`→空格、`\x0b\x0c`（Office 软换行）→换行、去 `\r`；单元格内换行转空格；
- `_fix_cjk_spaces`：**仅当空格两侧都是汉字才移除**（"度 假村"→"度假村"），"Disney 频道"这类中英文正常空格保留；
- 行宽不齐补空串 → 删全空行 → 裁全空列（PPT 图片/logo 占位列）。

**第二步：稀疏列裁剪 `trim_sparse_cols`（≥4 行的表才参与）**
列空值率 >80% 判稀疏，分三种情况处理而非一删了之：
- 仅表头有值（票价表"立即预订"按钮列）→ 整列连表头删除；
- 某行只有稀疏列有值（时间表分组标题）→ 文本提升，保留首列当标签行；
- 数据行偶发稀疏值 → 并入该行末列（防御逻辑，当前库 0 命中）；
- 至少保留一列。

**第三步：四元组判质决定表格命运**

| 判定 | 条件 | 处理 |
|---|---|---|
| 正常表 | 其余全部 | 渲染 Markdown，整块保留 |
| `degenerate` | 清洗后仅 1 行且非空单元格 ≤2 | 拼成一个普通段落（PDF 标题栏误判） |
| `giant` | 数据行 ≤2 且存在 >300 字巨型格 | 长格各自成段、短格攒尾段（Word"文本容器"伪表） |
| `unbalanced` | 最高列填充率 ≥0.75 且次高 ≤0.5 | 逐行成段 + 横向去重（COM vMerge 扁平化的标签-明细表） |

### 4.8 去重、短块合并、父子上下文、标签

**跨文件去重（emit 时）**
- hash = `sha1(去全部空白后的 body)`——用 norm 而非原文，换行差异不影响判重；
- 命中已存在块不新建，而是把当前来源 append 进该块 `sources`（file/category/orig_format/chunk_seq/heading），实现"一份正文、多来源可溯"；全库 **7 次**重复命中；
- 非表格块 body <8 字直接丢弃（MIN_CHUNK），表格不受限。

**短块合并 v2（finish 时，只在单文档 doc_order 内）**
- 对象：非表格且 body<100 字，合并后总长 ≤1200；
- 优先后向并入前一块，但必须同时满足：前块非表格 + `_same_heading`（heading 完全相同，防跨章节乱拼）+ 不超长；
- 后向不可行则挂起 pending 尝试前向并入下一块；被表格夹住的短块只能保留；
- 表格任何方向都不参与合并——这是 v1（短块并进表格制造半句 markdown 碎片）踩坑后加的硬约束。

**父子上下文（生成侧用）**
合并全部完成后，按最终 doc_order 为每块拼 `parent_context = 上一块尾300字 + 本块 + 下一块头300字`；线上 `build_context` 再对同源块做 suffix-prefix 重叠去重（`merge_overlap`），避免喂给 LLM 的上下文大段重复。

**自动标签**：12 个主题词库只从"文件名 + 分类 + 面包屑"命中抽取，不引入任何外部资料。

### 4.9 噪声过滤：规则为什么越收越窄

最初版本是宽正则，全库实测发现合法内容大面积误杀。最终每条规则都带长度/上下文闸门：

| 规则 | 闸门 | 全库实测命中 |
|---|---|---|
| "表格\n复制"导出占位 | 还要求总长 <80 | 少量 docx 残留 |
| 空表头碎片 | 仅含 `\|｜-—:：数字.` 且 <60 字 | 防御性 |
| 页脚模板 | 严格匹配"第X页(共/of)Y页" | 模板化文档 |
| `_is_empty_header` | ≤80 字且为目录/版权/序号/纯标点之一 | **0** |
| `_is_watermark_notice` | ≤120 字；命中 URL/©/版权词后剥掉通告片段，剩余实质中英文字符 <12 | **0**（"上海迪士尼乐园©周边酒店"、CRM 内网 URL 被闸门救下） |
| `_is_ocr_garbage` | ≥40 字且中英数有效字符占比 <0.35 | **仅 id=46 一块** |

方法论：先全库扫描统计候选命中，再按误伤反推阈值——0.35 不是拍的，是标定到"只命中 1 块纯符号乱码、零误杀"的结果。

### 4.10 切片层的一个重要连锁约束

每次重新 parse，chunk id 全部重排。因此任何解析改动必须连带执行：

```
重跑 1-parse_and_chunk.py → 重跑 2-build_index.py → 金标按 chunk_hash 自动重绑（remap）→ 重跑评估
```

漏掉任一步，下游数据全部失真（金标 gold_idx 绑定索引顺序）。早期做法是手动删除 `eval_qa_v2.json` 旧绑定重建；后来做了 chunk_hash remap（金标头带 `schema_ver=chunk_hash_v1`，索引重建后按内容 hash 自动重映射，miss 计数写入 remap 链），已免除手动删绑定——但**切片内容真变时 hash 对不上会 miss**，仍需核查 mapped/missing，miss 多时重新生成金标（见 9.4 与 `03` 第 10 章复核）。

## 5. 阶段 2：Embedding 与双索引构建

> 代码：[2-build_index.py](../2-build_index.py)

1. **长度探针**：正式批量前先 embed 全库最长 chunk，及早暴露模型输入长度限制；
2. **批量 embedding**：每批 8 条调 `tongyi-embedding-vision-plus`（百炼原生 contents 格式，经 AGICTO 网关），指数退避重试 3 次，**批量整体失败自动降级逐条**；
3. **断点续算**：文本向量缓存 `embeddings.npy`，重跑不重复计费；缓存带模型+dim 指纹，指纹不符自动判废重嵌；
4. **维度强校验**：实得维度 != `settings.EMBEDDING_DIM(1152)` 直接 SystemExit，防止换模型后混库；
5. **归一化 + IndexFlatIP**：所有向量 L2 归一化后 `faiss.IndexFlatIP(1152)`，内积即余弦；
6. **BM25 同批构建**：对全部 metadata content（含图片 OCR 文本）拟合字符 bigram BM25（`k1=1.5, b=0.75`，idf 用 `log(1+(n-f+0.5)/(f+0.5))`），pickle 落盘；
7. **FAISS 中文路径**：先写 ASCII 临时路径再 `shutil.move` 到位；
8. **构建报告**：`build_report.json` 分 stage1（解析）/stage2（索引）/stage3（图片）写产物计数、md5、9 项硬一致性检查（条数相等、hash 全覆盖且唯一、chunks 文件自 stage1 后未变等），stage2 汇总 `overall.ok`。

## 7. 在线查询全链路

> 代码：[frontend/app.py](../frontend/app.py)、[lib/retriever.py](../lib/retriever.py)

### 7.1 入口与公共设施

- `POST /api/query_stream`（SSE，默认）/ `POST /api/query`（非流式），两者共用 `prepare_turn`；
- 滑动窗口限流：每 IP 每分钟 30 次（`RATE_LIMIT_PER_MIN`）；
- 会话：内存 dict，上限 200 个、TTL 7200 秒，按 LRU 清理；每轮取**最近 6 条消息（=3 轮对话）**作历史（[app.py](../frontend/app.py)）。

### 7.2 意图层：规则门 + LLM 双轨

**规则门（不调模型、零延迟，始终生效）**
1. `_rule_gate_short_no_entity`：无会话历史 + ≤8 字 + 剥离疑问词/功能词/标点后零实体残留 → 直接 clarify。拦住"多少钱/几点开始/在哪买"；有历史的承接追问、含"门票/酒店"实体词、"天生一对是哪一年"这类含专名短问均不触发；
2. `_rule_split_multi_question`：≥3 个并列问号且 LLM 漏判多意图 → 按问号确定性强制拆分（只认问号，"也太坑了吧！"不触发）。
规则门以金标集 + QA 共 106 问 dry-run **零误伤**为准入条件。

**LLM 意图识别（qwen3.8-flash，可开关）**
- Step1 分 7 类：上下文依赖/对比/模糊指代/多意图/反问情绪/信息不足/明确；置信度阈值 0.6，低于阈值用原 query；
- 信息不足判定**极严格（宁缺毋滥）**：优先级最低，只要还能改写（指代消解/补全/拆分）就先改写，仅当历史也无线索且确属参数化事实查询才追问；
- Step2 按类型套专用改写 prompt：补全省略成分（禁止臆造）、指代消解、对比维度补全、情绪剥离、多意图拆成 ≤4 个独立子问题；
- 单会话连续追问上限 2 次（`INTENT_MAX_CLARIFY`），超了强行检索作答，避免死循环；
- 任何内部失败都降级为原句检索。

> 意图链路的完整深潜（一次真实提问的逐行走查、七项加固的实测贡献、金标口径修订的取舍与回滚）见 **第 16 章**。

### 7.3 向量化

子问题先经 `expand_query_terms` 注入同义词（`DISNEY_DICT`：上海迪士尼/达菲/FastPass/尊享卡等别名→标准名，同时加进 embedding 输入和 BM25 查询），再逐个调 embedding；服务端维护 256 条 LRU 向量缓存。

### 7.4 双路召回与 RRF 融合

- **向量路**：IndexFlatIP 余弦，`vec_k=max(k×4,20)`；有类别预过滤时扩到 `max(k×6,40)` 保证过滤后取满；
- **类别过滤是预过滤（allowed_idxs）而不是事后过滤**；
- **BM25 路**：字符 bigram（无 jieba），topk 同 vec_k；
- **RRF 等权融合**：每路贡献 `weight/(60+rank+1)`，默认 weight 各 0.5；融合池取 rerank_topn=**12**（不 rerank 时取 max(k×3,12)）。位次融合避免了两路分数量纲不可比的问题。

### 7.5 R4 预过滤

body <8 字的非表格块剔除；剔除后不足 k 时从向量序回填有效块。

### 7.6 Rerank 多级降级链

- 链路：**qwen3-rerank@AGICTO（首选）→ qwen3-rerank@百炼（兜底）**；早期首选是 Cohere rerank-v3.5，因其账户长期欠费每次必失败白增延迟，2026-10-02 移出默认链（可经 `.env` 加回）；百炼自动排除 Cohere 系列模型；
- AGICTO 走 Cohere 风格 REST `/v1/rerank`，百炼走 dashscope SDK 原生协议，按平台自动适配；
- **"HTTP 200 空 results" 判为失败**（欠费/故障信封），空结果也计入降级——禁止静默空转；
- **确定性失败码（401/403/404/insufficient_quota/Not enough money/payment method）立即 break 不重试，并熔断该级 10 分钟**（`_CIRCUIT`，TTL 600s）：欠费状态不会自愈，熔断避免每个查询白付一次 HTTP 往返+退避（事故期每查询曾白等约 6 秒）；成功后自动解除熔断；
- 计数器 `RERANK_STATS{calls, fallbacks, last_model, last_source, circuit_skips}` 全部走 `_STATS_LOCK`，20 线程并发压测无丢失；
- 展示给用户的相似度始终用**原始余弦**（rerank 分不直观）；
- rerank 用的查询：单意图用消解后的查询；多意图用"原句 + 各子问题"——既保整体意图又带上补全的实体。

### 7.7 MMR 多样性（位次版，k≥3 才开）

标准 MMR 贪心：`score = λ·相关性 − (1−λ)·与已选集合的最大余弦相似度`。本项目的关键修改在**相关性项**：

- 旧实现用原始向量余弦做相关性，在 1152 维新空间下纯向量 Recall 仅 0.558，等于把 rerank 辛苦排出的顺序整体丢弃（详见第 10 章）；
- 现实现（[retriever.py](../lib/retriever.py)）：相关性改为**池内位次线性衰减** `rel=(n−j)/n` 继承 rerank/RRF 的排序信号，多样性项才用向量余弦；
- 默认 λ=0.72；多意图路径 λ_multi=0.55（候选跨子问题、冗余风险更高，待多意图金标验证后定标）。λ≤0.4 的方向已在 82 题标定中否决：recall@5 0.854 vs 0.915（-6.1pt，`diag_calib.json`），详见 `03` 第 10 章复核。

### 7.8 同源限额

`max_per_source=3`：单个文件最多返回 3 条。超限时**先跨源回填**（从向量序找其他文件的块），全库都没有同源之外的候选才放宽限额；至少保留单源护栏。
（限额经过标定：cap=1 Recall 0.756，cap=2 0.915，cap=3 0.951，不限 0.951——cap=3 与无限额持平。）

### 7.9 多意图合并检索

`search_multi`：各子问题的向量路 + BM25 路全部进入**同一个 RRF 池**累加（而非各自截断 top_k 再合并，避免子问题互相挤占），之后统一 rerank（用原问题防语义偏移）、MMR 用主意图（第一个子问题）向量。

### 7.10 图片媒体匹配（gap rule）

文本检索之外，用主意图向量全库扫图片（仅 481 条，开销可忽略）。匹配逻辑（[app.py](../frontend/app.py)）：

- 先过绝对阈值 `MEDIA_SIM_THRESHOLD=0.45`；
- top1 与 top2 差距 < `MEDIA_GAP=0.02` 视为视觉歧义 → 对候选图片（取前 3）直接打 **BM25 词面分**决胜；都无词面命中则放弃匹配；
- **阈值校准的教训**：早期按全库 BM25 max 校准，图片 OCR 文本短、永远够不到阈值，图片永远不出现；改为按**图片候选池自身**相对比较后修复。
- 待办：0.45/0.02 目前仍标注"待图片金标集标定"。

## 8. 生成侧：上下文、Prompt、流式与会话

### 8.1 上下文组装 `build_context`（[retriever.py](../lib/retriever.py)）

- 按来源（文件）归并：同源多块用 `parent_context` 拼接，邻块之间做 suffix-prefix 重叠去重；
- 每个来源编号 `[n]`，头注 `来源: 文件名 | 章节: headings`，供模型行内引用；
- 返回 `(context_str, refs)`，refs 供前端做 chunk 卡片锚点。

### 8.2 强约束 System Prompt（线上单一真源）

5 条规则（[lib/settings.py](../lib/settings.py)）：
1. 只能依据背景知识回答，不得编造，知识不足要明说；
2. 价格/时间/身高/政策等数值必须准确引用，禁止估算；
3. 每个事实结论后 `[n]` 标注来源，多来源标多个；
4. 结构化信息优先 Markdown 表格，单元格里也要带来源编号；
5. 专业友好、简洁有条理。

前端还**确定性追加**"参考来源"文件清单（`render_refs`），不依赖模型自觉输出；`[n]` 标记可点击跳转 chunk 卡片。线上 prompt 有 sha1 指纹，前端与评估"线上同 prompt 档"逐字同源。

### 8.3 SSE 流式（[app.py](../frontend/app.py)）

- 检索管线放在工作线程，阶段边界（rewrite/embed/retrieve/rerank/generate）经 `queue.Queue` 实时推给 SSE 生成器——前端"工作人员模式"看到的是**真实阶段**而非定时器假进度；rerank 降级/失败也走阶段 detail 透传；
- 事件顺序：`stage*` → `meta`（chunks/refs/trace）→ `token*`（流式正文）→ 末尾确定性来源清单 → `[DONE]`；
- 网关错误透传：`!resp.ok` 时读 JSON error 体（欠费时前端红气泡直接显示"AGICTO 账户余额不足…"），而不是笼统的 500。

## 9. 评估体系（本项目最值钱的部分）

> 代码：[4-evaluate.py](../4-evaluate.py)；产物：`output/eval_results.json`（`{config, results}`，tmp+replace 原子落盘）

### 9.1 金标集

| 金标 | 规模 | 用途 | 特点 |
|---|---|---|---|
| 检索 QA | **82** 题 | Recall@k / MRR | 从 chunk 反向生成、含金标答案与 gold_idx，每来源文件限额 2 条缓解同源偏差；规则匹配（`_keys_hit`）可离线精确复现 |
| 答案 QA | **80** 题 | 证据/答案侧指标 | 在检索 QA 上剔除 2 题不适合生成判定的 |
| 意图金标 | **24** 题 | 意图链路 | 人工标注，**不绑索引**，随意图链路演进扩充 |

每条 QA 携带 `chunk_hash`（切片阶段内容 sha1），加载时按 `born_index_md5 → 当前 index_md5` 用 hash **重映射 gold_idx**，记录 kept/missing；命中率丢失超 50% 才判尺子失效。重建索引不再让评估归零。

### 9.2 三层指标（防注水的关键设计）

答案侧判定（`answer_hit`，[4-evaluate.py](../4-evaluate.py)）严格拆分：

- `evidence_coverage`：金标关键事实（**全部数字**必中 + ≥ceil(一半) 的 2 字以上实体词；中文数字归一"七→7"）是否出现在**检索上下文**里；
- `answer_hit`：同样的事实是否出现在**生成答案**里（只数 ANSWER，不数 context）；
- `answer_hit_given_evidence`：证据到位条件下的答对率——**这才是生成侧真实水平**；
- `gen_loss_when_evidence`：证据在却答错的比例。

早期 v1 把 context 拼进判定串，检索到了就算答对，生成质量被注水（answer_hit 虚高、与 Recall 近饱和矛盾），strict 口径修复。online 档判定前还会剥离 `[n]` 引用标记——来源编号可能恰好包含金标数字（如 [1]）。

**为什么检索 Recall@5=95.1% 而证据覆盖只有 65%（必须能解释）**：
1. 判定对象不同：Recall 是"gold chunk 这一块在不在 top5"的**块身份**匹配；证据覆盖是"金标**答案的关键事实**（所有数字+半数实体词）在不在组装后的上下文里"，严格得多；
2. 有些题的金标答案需要综合多个块的信息，单块命中不够；数字写法/口径不一致也算未覆盖；
3. 口径配置不同：95.1% 是检索档，65% 是线上口径（MMR+限额）答案档；
4. 这两个数一起看恰恰说明"检索到块"≠"证据可用"，也是还要继续优化的短板。

### 9.3 评估档位矩阵

- 检索侧：纯向量 / 混合 / 混合+Rerank（均 k=5）；**2×2 网格** {k=3,k=5}×{后处理关,后处理开(MMR+限额)} 分离 k 与后处理净贡献；线上改写 query 档（与 k5 后处理开仅 query 来源不同，量化改写净贡献）；阈值扫描 2 行仅参考；
- 答案侧：2×2 网格（short 评估 prompt）+ **线上同 prompt 档**（客服 system + `[n]` 编号上下文，与 app.py 逐字同源）+ 无 rerank 基线；
- 意图两档：QA 集 action 分布统计 + 24 题人工金标（action 准确率/clarify P/R/F1/类型命中/多意图/消解词保留率）。

|---|---|---|
| 纯向量 | 0.561 | 0.375 |
| 混合 BM25+向量 | 0.805 | 0.582 |

### 9.4 评估可信度的三道机制化防线（三个事故换来的）

1. **index_md5 指纹守护**：评估产物头部固化索引 md5；启动时校验，不一致拒绝复用旧结果。起因：一次主评估 01:51 落盘、MMR 修复 02:16 才落盘，整批旧口径数值还在被当现状引用；
2. **对照档必须与线上同配置**：曾拿"关 MMR、无限额"档的 k 值数据去决策"开 MMR"的线上配置，判据无效；此后要求 2×2 对照 + 一个与线上逐字同配置的档，label 与参数同源；
3. **诊断脚本必须入库**：diag_pool/diag_mmr_fix/diag_answer_k 曾由仓库外临时脚本生成、零引用、无法复现 → 固化为 `5-diagnose.py`，产物头部写全 `{model,k,use_mmr,mmr_lambda,max_per_source,index_md5,gen_ts}`。

审核方法论沉淀为"**四线交叉**"：脚本（代码在不在仓库）→ 产物（配置/指纹/时间戳）→ 缓存（键是否含全部因子）→ 日志（有没有真实运行痕迹）。

### 9.5 缓存与并行：评估工程提速

80 题 × 多档位矩阵串行要几十分钟，优化手段：

- **线程池 8 worker**：`ThreadPoolExecutor` + `as_completed`，**按下标保序收割**；检索+生成在同一 worker 内完成，不拆两段；每 10 题 checkpoint 落盘；
- **embedding 串行预热**：提交线程池前主线程先把全部 query 向量算进 dict（普通 dict 非线程安全），预热后 worker 只读；跨档位复用；
- **OpenAI client 模块级单例**：旧实现每次新建客户端 → 320 次重复 TLS 握手，是主要耗时源之一；
- **答案磁盘缓存全因子键**：`sha1(模型 | prompt版本 | index_md5 | k | MMR | λ | 限额 | prompt风格 | 问题 | 上下文)`——不同档位检索到相同上下文直接命中不重调 LLM；**失败不缓存**；文件头指纹不符整份作废；改 prompt 必须 bump `_ANS_PROMPT_VER`；
- **改写缓存三处共用**（改写档/意图评测/意图金标）；
- 砍掉逐档重复的答案档（两个档参数逐字相同）→ 生成调用 **320 → 240**；删掉每题 `sleep(0.2)` 礼貌性节流（有 429 指数退避就够了）。

最新一轮 ans 缓存 480 命中 / 0 miss、改写缓存 80 命中，总耗时 1225.9 秒（含首次未缓存的运行）。
可迁移经验：**连接池单例省 TLS、全因子磁盘缓存省重复调用、线程池保序收割省墙钟；而一切复用的前提是指纹同源校验，否则提速只是更快地产生错误数据。**

## 10. 标杆案例：MMR 暴跌 47.7pt 的完整排查

> 简历核心亮点，必须能脱稿讲。特征：**没有急着调参，先打点证伪假设，再用消融锁定因子，最后读算法定位根因。**

**第 0 步：立规矩**——"先查候选池，再动 λ"，直接避免一整晚无效调参。

**第 1 步：分段打点，证伪"阈值砍池"假设。**
在 search 各阶段加 POOL_STATS：`rrf_out=12 → after_r4=12 → rerank_out=12 → mmr_in=12 → final=5`。结论：候选池全程无裁剪；媒体阈值不在文本管线上。最顺手的假设被证伪。

**第 2 步：单因素消融，锁定肇事者（k=5, n=86）**

| 档 | Recall@5 | 相对无后处理 |
|---|---|---|
| A 无后处理 | 0.884 | — |
| B1 仅 MMR | **0.407** | **−47.7pt，独自造成全部损失** |
| B2 仅限额2 | 0.860 | −2.4pt（噪声级） |
| C MMR+限额 | 0.419 | ≈ B1 |

**第 3 步：读算法找根因。** 旧 `_mmr_select` 相关性项用原始余弦 `vecs @ q`：当时新向量空间下纯向量 recall 只有 0.558，等于把 rerank 排出的 12 池顺序**整体丢弃**、退回最弱信号；所以 λ→1 也只能回到纯向量水平，**调 λ 在数学上无解**。

**第 4 步：修复**——相关性项改为池内位次线性衰减 `rel=(n−j)/n`，继承 rerank/RRF 序；多样性项保留向量余弦。

**第 5 步：同参数对照验证**

| 档 | 修复前 | 修复后 |
|---|---|---|
| MMR λ0.72 | 0.407 | **0.884** |
| MMR+限额2 | 0.419 / MRR 0.329 | **0.860 / MRR 0.770（+44pt）** |

后续在 1152 维新索引上重标定：限额 1/2/3/不限 = 0.756/0.915/0.951/0.951，线上定稿 **k=5 + cap=3 + λ=0.72**，Recall@5 = 0.951，多样性零损失。

**可复用 SOP**：① 先立"不准调参"的规矩；② 沿管线分段打点把损耗夹逼到两阶段之间；③ 主动证伪自己最顺手的假设；④ 单因素消融一次只开一个开关；⑤ 读公式，追问每个输入信号来自哪里、有没有丢掉更强的上游信号；⑥ 修复后用完全相同参数对照，再重启真实服务烟测收尾；⑦ n≈80 小样本不报小数点后第三位的差异。

## 11. 线上事故与异常处理机制

### 11.1 AGICTO 全站欠费：HTTP 200 包着错误信封

- **现象**：查询 500，health/索引正常；rerank 按预期降级，但 embedding 函数拿到 `embs=None` 继续跑 → TypeError 500；
- **根因**：OpenAI 兼容网关对欠费返回 HTTP200 + `error.code=insufficient_quota`，旧代码只认 `data` 字段；
- **修复**（[app.py](../frontend/app.py)）：错误码稳定映射表给用户可读提示；取不到 embs 直接抛显式 RuntimeError，不许 None 往下游流；SSE 路径读取 JSON error 体透传前端；rerank 确定性失败立即 break 不重试，欠费时每查询省约 6 秒。
- **通用教训**：**OpenAI 兼容网关会用 200 包业务错误，不能只判 HTTP 状态码**；错误信息要一路透传到用户看得见的地方。

### 11.2 模型/平台兼容

- tongyi-embedding-vision-plus 曾在 AGICTO 报 IllegalInput，应急换 text-embedding-v3（1024 维）并删库重建；现网已回到 vision-plus（1152 维）。**换 embedding 模型必须删 embeddings.npy + .faiss**，启动有维度 assert 兜底；
- rerank 主链多次调整，模型名变动必须同步 settings 默认值、.env、README、docstring，否则口径漂移。

### 11.3 前端两个隐蔽坑

- **反斜杠路径**：`rel_path` 含 `\` 拼进内联 `onclick` 单引号字符串，`\x` 被 JS 当未知转义吞掉，灯箱退化为单图、图片 404 → 一律改 `data-rp` 属性 + `dataset.rp` 传值；
- **bfcache**：重建索引后浏览器显示旧向量数，实为 bfcache 旧页面 → 硬刷新验证，数据以 `/api/stats` 实时返回为准。

## 15. 可迁移的方法论（一页总结）

**切片**
- 宁可块稍大，不可句被切断；结构（标题栈/幻灯片边界/章节词典/Markdown 表）是免费的高精度信号；
- 每个上游库的输出都要有"判质+降级"层：COM 扁平化制造稀疏表、PyMuPDF 误判标题栏和双栏；
- 同一份内容只保留一条通道；不可逆动作（分配 id）放最后；
- 启发式三问：全库命中哪些？误伤哪些？阈值依据是什么？答不上来不许进主线。

**检索**
- 双路位次融合（RRF）优先于分数调权；rerank 是最大单点增益（0.805→0.951）；
- 每加一个后处理算子都要回答：它用的信号来自哪里？有没有把更强的上游信号丢掉？
- 参数（cap/λ/阈值）只信标定网格，不信手感；标定结论先落 diag 产物再回写默认值。

**评估**
- 没有可信的评估，所有优化都是自我感觉良好；先审指标的分母和统计范围，再看数值；
- 单因素消融、对照档与线上同配置、产物 mtime 对代码 mtime、数据必带来源指纹；
- 任何影响决策的数据，生成它的代码必须在仓库里。

**工程**
- 批量 LLM 提速三板斧：连接池单例、全因子磁盘缓存、线程池保序收割；复用前提是指纹同源；
- 200 也要查信封体；确定性失败快速降级 + 熔断；错误信息一路透传到用户；
- "做了"和"可证明做了"是两回事——烟测脚本化、日志结构化、健康检查可交叉核对。

**排查 SOP**
- 效果异常：对时间线 → 查指纹 → 分段打点 → 单因素消融 → 读信号流向 → 同参数对照 → 小样本慎报差异；
- 切片异常：从异常 chunk 面包屑反推源文件位置 → 判分支 → 全库标定 → 重建+删金标+硬刷验证；
- 线上报错：先 /api/health → 抓包看状态码和信封体 → 确认平台/key/余额 → 确认解释器与端口占用进程。

#### 16.1.1 一个真实提问的完整走查：「它多少钱？」

以下用意图金标里的一条真实样本（135 条之一）走完全程。所有数值均来自
`output/intent_gold_eval_after_gold_revision.json` 的实跑记录（2026-10-20，加固后），可逐字复核。

**输入**

| 项 | 值 |
| --- | --- |
| 会话历史（sess_get 取到的 1 轮） | user：玲娜贝儿玩偶哪里买？<br>assistant：园区商店和官方商店有售。 |
| 当前 query | `它多少钱？` |

**逐阶段实际行为**

| # | 阶段 | 实际发生什么 | 产物 |
| --- | --- | --- | --- |
| 1 | 门 1 短问无实体 | **有历史 → 不触发**（承接性追问必须走 LLM 消解） | — |
| 2 | 门 2 三连问 | 只有 1 个问号 → 不触发 | — |
| 3 | Step 1 LLM | 结合历史识别出 `context_dependent + pronoun` 两类 | `query_types=[context_dependent, pronoun]`，confidence ≥ 0.6 |
| 4 | 预算重置 | Step1 调用返回，`_budget.t0 = now`，Step2 预算 18s 起算 | — |
| 5 | clarify 判定 | 模型未要求澄清；且存在可改写类型（指代可消解）→ **不追问** | action 保持 retrieve |
| 6 | Step 2 串联改写 | 按优先级先走 context_dependent 补全、再走 pronoun 消解，共 2 次 LLM 调用 | `玲娜贝儿玩偶多少钱？` |

**两个值得注意的细节**

- **`elapsed_ms=9117` 只是 Step2 阶段耗时**（第 6 步那 2 次调用），不是整条链路耗时——计时起点在第 4 步才重置。Step1 本身还要约 10-15s。全链路约 20s 量级。
- **消解质量可度量**：金标给这条题定的 `must_include=["玲娜贝儿"]`，改写结果里含该词 → `term_hit=true`。如果 Step1 超时降级，queries 会退化成原句 `它多少钱？`，检索质量塌掉但 action 仍然"正确"——这就是为什么要单独看 `term_keep_rate` 而不是只盯 action_acc。

**同一套链路在其他输入下的分流**（均来自同一次实跑）：

| 输入 | 命中路径 | 结果 |
| --- | --- | --- |
| `多少钱`（无历史） | 门 1 | 直接追问："能补充一下具体对象吗？例如门票价格、身高限制…" |
| `门票多少钱？停车怎么收？演出几点开始？` | 门 2（前置） | 不等 LLM 先拆成 3 段：`[门票多少钱, 停车怎么收, 演出几点开始]`，LLM 只做细化 |
| `下雨天还开吗？`（历史聊过烟花） | Step1+Step2 | 改写为 `今晚的夜光幻影秀下雨天还开吗？`（术语规范化） |
| 系统提示词泄露测试（对抗样本） | Step1 遇内容审核异常 | `degraded=true, degrade_reason=step1_exception`，按原句检索，结果仍正确 |

### 16.2 意图链路内部：三步 + 两道门

#### 16.2.1 两道确定性规则门（不调模型，零延迟，零幻觉风险）

| 门         | 触发条件                            | 动作                 | 代码位置                                      |
| --------- | ------------------------------- | ------------------ | ----------------------------------------- |
| 门 1 短问无实体 | 无历史 + ≤8 字 + 无实体词 + 剥离功能词/标点后为空 | 直接 clarify         | `retriever.py:_rule_gate_short_no_entity` |
| 门 2 三连问   | 问号切分后 ≥3 个有效问句                  | 强制 multi_intent 拆分 | `retriever.py:_rule_split_multi_question` |
| 门 3 无历史指代（S4 新增） | LLM 判 retrieve 后：`need_clarification=false` ∧ `underspecified ∈ query_types` ∧ 无会话历史 ∧ query 含指代词（这个/那个/那里/这些/那些/它们/其它/它） | 改判 clarify         | `retriever.py:intent_rewrite`（`pronoun_gate_hit` 计数） |

门 1 的反向护栏（三条，任一命中即不触发）：有会话历史、含领域实体词（门票/酒店/迪士尼…）、  
剥离后仍有残留（"天生一对是哪一年"剩"天生对"）。

**2026-10-20 变更**：门 2 原本放在 Step1 之后，一旦 Step1 超时降级就 `return fallback`，  
门 2 根本没机会执行。实测"门票多少？酒店多少？停车多少？演出几点？"这类题在超时轮次全部漏判。  
现已**前移到 LLM 调用之前**，纯字符串切分不依赖任何模型输出，LLM 成功时再叠加其更细的拆法。

#### 16.2.2 LLM Step 1：意图识别

输入 = Step1 prompt（1324 字，含 7 类定义与优先级）+ 最近 3 轮历史 + 当前 query；  
输出 JSON `{query_types, need_clarification, clarification_question, rewritten_query, confidence}`。

七类类型与执行优先级（`_TYPE_PRIORITY`）：  
`multi_intent > rhetorical > context_dependent > pronoun > comparison`，另有  
`underspecified`（信息不足，直接短路追问）与 `clear`（明确型，按原句检索）。

**优先级设计的用意**：能改写就别追问。只有当"无任何可改写类型"且模型要求澄清时才追问——  
因为强行追问会打断指代链（"你刚提到的人物在哪见"本可消解出实体，追问反而丢上下文）。

#### 16.2.3 LLM Step 2：分类型改写

按命中类型**串联**执行（多意图先拆，再对每个子问题走消解链）。  
例：`multi_intent + pronoun` → 先按问号/语义拆成 N 个子问 → 每个子问再单独做指代消解。

**这一层直接决定"召回是否有用"**：消解成功时检索查询从"它多少钱"变成"玲娜贝儿玩偶多少钱"，  
embedding 从一个泛化向量变成精确实体向量，召回质量差一个量级。

### 16.4 金标与各类参数，在真实问答中到底起什么作用

这是最容易被误解的部分，逐项澄清：

#### 16.4.1 金标文件：**不参与线上问答**

| 文件                       | 读取方                                      | 线上问答时是否生效                       |
| ------------------------ | ---------------------------------------- | ------------------------------- |
| `eval_intent_gold.json`  | 仅 `4-evaluate.py:evaluate_intent_gold()` | **否**。它是评估尺子，不进 `app.py` 任何代码路径 |
| `output/eval_qa_v2.json` | 仅 `4-evaluate.py:load_or_build_qa()`     | **否**。检索/答案评估用                  |

所以金标**不会改变用户得到的答案**，它只决定"我们以为的准确率"是否可信。  
7- 版本 n=24 时全 1.000，真实水平其实更低——金标小，指标就虚高，与系统无关。

**间接影响（金标驱动开发）**：`retriever.py:511` 的注释写明门 1 是  
"P1-7（2026-10-02，金标 eval_intent_gold.json 驱动）"——金标曾驱动出规则门 1 这个功能。  
这是它唯一进入线上代码的路径，且是**离线开发决策**，不是运行时依赖。

#### 16.4.2 阈值参数：真正在运行时生效

| 参数                                                              | 默认                  | 运行时作用             | 生效条件                               |
| --------------------------------------------------------------- | ------------------- | ----------------- | ---------------------------------- |
| `INTENT_CONFIDENCE_MIN`                                         | 0.6                 | 低于此值按原 query 检索   | `use_rewrite=True` 且 Step1 返回      |
| `INTENT_MAX_SUB_QUERIES`                                        | 4                   | 多意图最多拆几个子问题       | 同上                                 |
| `INTENT_MAX_CLARIFY`                                            | 2                   | 单会话连续追问上限，防死循环    | `frontend/app.py:sess_clarify_get` |
| `INTENT_TIMEOUT` / `INTENT_MAX_RETRY` / `INTENT_BACKOFF_BASE`   | 45 / 2 / 0.8        | **2026-10-20 新增** | 每次 LLM 调用                          |
| `BM25_WEIGHT` / `MMR_LAMBDA` / `MAX_PER_SOURCE` / `RERANK_TOPN` | 0.5 / 0.72 / 3 / 12 | 检索后处理             | 每次检索                               |

#### 16.4.3 一个容易被忽略的事实：`use_rewrite` 默认是开的

`frontend/templates/index.html:540` 的 `tRewrite` 复选框 `checked`，  
即前端默认发送 `use_rewrite=True`。**只有用户手动取消勾选，意图改写才完全不执行。**

#### 16.4.4 金标的优先级：服务于"回答更准"，而不是反过来

你指出"金标只是参考，最终目标是让回答更准、召回更有用的样本"——这与本次改造的方向一致，  
本项目按以下优先级执行：

| 优先级 | 目标             | 判据                    | 金标的角色                    |
| --- | -------------- | --------------------- | ------------------------ |
| 1   | **回答更准、召回更有用** | 端到端：证据覆盖、答案命中、消解词保留   | 金标是**观测工具**，不是优化目标       |
| 2   | 改写链路稳定不抖动      | 真降级率、单问延迟上界           | 金标提供口径，指标看 `degraded` 标记 |
| 3   | 指标好看           | action_acc / type_hit | **最低优先级**——不因指标牺牲 1、2    |

实践体现：

- 预算闸门在超时场景下**主动放弃改写**（term_keep 会掉），因为"不卡住回答"优先于"改写更漂亮"；
- 金标修订（2026-10-20 第二轮）先确定"正确行为"再改标注去匹配，而不是把系统现在的输出
  直接封为正确答案——10 条修订每条都有独立理由，写入 `label_rules` 与 `revision_2026_10_20` 留档；
- 唯一保留的 action 分歧（`这个项目适合我吗？`）**不许修订掩盖**：它是真实的系统缺口
  （LLM 标了 underspecified 却不追问），留作观测项，见 5.3 与第七章；
- 本次优化的验收标准是**真降级率归零 + term_keep 回升**，而不是让任何单一指标最大化。

一句话：**金标用来发现真问题，不用来证明自己对**。

### 16.5 "标注过严"是什么、不修正会有什么影响

#### 16.5.1 问题规模：最终基线剩余 15 条分歧

加固后基线（`intent_gold_eval_after_opt.json`）实测剩余 15 条未通过样本，逐条复核后
分为两类——**标注过严（改尺子）** 与 **真实系统问题（留观测）**：

| Query | 原金标 | 系统实际 | 判定 |
| --- | --- | --- | --- |
| 年卡价格是多少？ | clarify | retrieve（判 clear） | 标注过严：年卡是库内自包含实体 |
| 酒店多少钱一晚？ | clarify | retrieve（判 clear） | 标注过严：库内酒店可枚举，价格浮动可泛化作答 |
| 员工票怎么转让？ | clarify | retrieve（判 clear） | 标注过严：主体齐全，意图链路不判"库内有无" |
| 小孩要买票吗？ | context_dependent | retrieve（判 clear） | 标注过严："小孩"是明示主体而非省略 |
| 停车费能免吗？ | context_dependent | retrieve（判 clear） | 标注过严："停车费"明示主体 |
| 还有别的吗？ | must_include=创极速光轮 | 改写继承"低幼项目"话题 | 标注过严：应度量最近话题继承，不追溯首轮实体 |
| 吃饭怎么解决？ | must_include=餐 | 改写为"园区内吃饭怎么解决？" | 口径错误："吃饭"与"餐"不同形，子串匹配天然失败 |
| 下雨天还开吗？ | must_include=烟花 | 改写为"…夜光幻影秀…" | 标注过严：系统做了术语规范化，比 gold 更精确 |
| wifi有吗？ | must_include=无线 | 改写为"园区内是否有WiFi？" | 口径错误：用户原词即规范词，"无线"是历史回答用词 |
| 俺就想问问乐园里边吃饭咋收费 | must_include=餐 | 原句检索 | 口径错误：同"吃饭≠餐"；本句自包含，不设要求 |
| 这个项目适合我吗？ | clarify | retrieve（标了 underspecified 却不追问） | **真实系统问题，保留观测** |

（另有 2 条 must_include 在扩充构建时已修正：`这个要预约吗？` 要求保留"夜光幻影秀"而非"演出"，  
`那里卖什么？` 要求"M大街"而非"商店"——同属标注口径错误，系统消解更精确。）

#### 16.5.2 不修正的影响：分短期与长期

**短期（对指标）**：无实质功能影响，但尺子失真。clarify R 被 3 条过严样本压到 0.733、
term_keep 被 5 条口径错误压到 0.903——**系统实际更好，账面却更差**，后续所有优化都建立在一个
偏低的基准上，改善量被系统性低估。

**长期（真正危险）**：

1. **尺子失准会掩盖真实退化**。若将来改 prompt 导致 clarify 召回真的从 0.95 掉到 0.6，  
   而金标本身有若干条是"错的"，团队就无法区分"退化"与"标注误差"——  
   **评估尺子一旦掺水，所有基于它的决策都不可信**。这是最实质的风险。
2. **为凑指标而反向劣化系统**。若把金标当 KPI（比如"action_acc 必须 >0.98"），  
   就会有人去改系统去迎合这几条：比如把"酒店多少钱一晚"也判成追问。  
   结果是**用户体验变差而指标变好**——指标与目标脱钩，比指标低本身更危险。
3. **口径不写下来，下一代维护者会重复踩**。这些分歧背后是"知识库可枚举/泛化作答时直接检索"  
   "must_include 取可靠词形"两条隐含原则，不写进 label_rules 就会随人员流动丢失。

#### 16.5.3 实际怎么修正的（2026-10-20 已执行）

经确认"金标只是参考、最终目标是回答更准"，按**先定目标行为、再改标注匹配**的顺序完成修订，
全部记录在 `7-build_intent_gold.py` 文档字符串与金标 `__meta__.label_rules` / `revision_2026_10_20`：

**第一步：口径写进 label_rules（零风险）**

```
"clarify_scope": "clarify 仅用于'缺少必要主体且无法从历史/知识库补全'的提问；单度假区
  知识库内'哪个园区'不构成缺失，知识库可枚举或可泛化作答时一律 retrieve（宁检索不追问）。
  仅当查询完全无法从历史获得线索、且确属参数化事实查询时才追问。"
"term_scope": "must_include 须取改写后实际会出现的词形：同义不同形（吃饭≠餐）或口语/规范名
  差异（烟花 vs 夜光幻影秀）不计未保留，改用可靠词形或置空；clear 题不设 must_include。"
```

**第二步：逐条改判（10 条，均有独立理由）**

- 3 条 underspecified → retrieve：`年卡价格是多少？`（自包含实体）、`酒店多少钱一晚？`
  （可枚举+可泛化）、`员工票怎么转让？`（主体齐全，检索不到由回答层诚实降级）；
- 2 条 context_dependent → clear：`小孩要买票吗？`、`停车费能免吗？`（明示主体，非省略主语）；
- 5 条 must_include 修订：`还有别的吗？`→"低幼"（度量最近话题继承）、`吃饭怎么解决？`→"园区"
  （改测"园区内"补全）、`下雨天还开吗？`→"夜光幻影秀"（术语规范化）、`wifi有吗？`→"WiFi"
  （用户原词）、`俺就想问问吃饭咋收费`→置空（本句自包含）。

**第三步：保留 1 条真实观测项**

`这个项目适合我吗？`（无历史）**不改判**：无历史 + "这个"无法消解，追问是 prompt 判定标准下的
正确行为；而系统的实际输出自相矛盾——`query_types` 标了 underspecified，
`need_clarification` 却是 false 且未改写。这是**真实的系统缺口**（LLM 输出自相矛盾），
改金标去迎合它等于掩盖问题。修订后它成为唯一 1 条 action 判错，action_acc=0.993 如实呈现。

**复测方式**：query 集合未变，`9-export_intent_eval.py` 命中改写缓存 135/135，
严格复现上次真实 LLM 运行结果（含 degraded/elapsed_ms），只换尺子重算——
保证"系统零改动，只有标注变"可被验证，而不是又跑出一组新数字。

### 17.3 各阶段"完成"的定义（工程纪律）

每个 S 阶段收尾必须四件套齐全，缺一不算完成：

1. **有产物**：`output/` 留痕且带指纹（index_md5 / 模型链 / 时间戳）；
2. **有读数**：与既有基线逐档对比，不只报绝对值；
3. **有结论**：达标与不达标都写清——S3 的负结论与 S7 的正结论同等价值；
4. **有回滚**：改动清单 + 索引备份（如 `output/backup_pre_dualvec/`）。
