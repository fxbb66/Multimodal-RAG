## 一、环境与基础设施类坑（09-29，建项目初期）

这一批坑的共性：**Windows + 中文路径 + 多 Python 解释器 + Office COM**，每一个都能浪费半小时以上。

### 1. 全局 Python 装包失败
- **现象**：装 networkx 等包时报权限错误，`networkx-3.6.1.dist-info` 目录无法写入。
- **根因**：全局解释器 `C:/Python313` 安装在受保护目录。
- **对策**：所有脚本一律走项目虚拟环境 `.venv\Scripts\python.exe`，并固化为项目硬约束。

### 2. FAISS 不支持中文路径
- **现象**：`faiss.read_index` 在中文目录下直接失败。
- **根因**：FAISS 的 `read_index` 底层是 C 标准库 `fopen`，Windows 下对非 ASCII 路径支持差。
- **对策演进**：
  1. 初期：索引文件用相对路径 `"disney_index.faiss"` + `os.chdir(PROJECT_ROOT)`；
  2. 后期（去掉 chdir 副作用）：`retriever.ascii_faiss_path` 复制一份 ASCII 临时路径再加载，构建时 temp 文件写完再 move。

### 3. PowerShell 编码与后台进程
- **现象**：含中文的 `.ps1`（0-转换旧格式.ps1）运行时乱码。
- **根因**：PowerShell 5.1 把无 BOM 的 UTF-8 文件按 GBK 解析。
- **对策**：用 PowerShell 7 执行（`& path.ps1`），不要用 `powershell -File`。
- **附带坑**：`Start-Process -WindowStyle Hidden` 起的服务间歇性 502；改为 venv python 直接后台运行才稳定。重启服务时还要确认旧进程是不是全局 Python 跑的（曾发生旧进程占着 5001 端口）。

### 4. COM 转换的盘符大小写
- **现象**：`.doc→docx` 转换后按 manifest 查文件全部 miss。
- **根因**：COM 写的 manifest.json 里是大写 `"D:"`，而 `os.walk` 返回小写 `"d:"`，字典键对不上。
- **对策**：`os.path.normcase` 统一归一化后再比对。

### 5. pip 镜像
- tuna 镜像在 package CDN 上返回 403，实际可用的是 repo.huaweicloud.com；沙箱里写 `.pyc` 被拦时设 `PYTHONDONTWRITEBYTECODE=1`。

## 二、数据切片类坑（09-29 ~ 10-01，反复重建索引最多的部分）

切片层的坑有一个共同放大器：**每次重新 parse，chunk id 全部重排**。因此任何解析改动都必须连带：重跑 `2-build_index.py` → 删除 `eval_qa_v2.json`（金标 gold_idx 绑定索引顺序）→ 重跑评估。漏掉任何一步，下游数据全部失真。

### 1. PPT 图表变成纯数字噪声表
- **现象**：切出大量只有 `212.99 / 轴刻度 / 数据点` 的宽数字表。
- **排查**：读 python-pptx 形状类型，发现柱状图/饼图是 `MSO_SHAPE_TYPE.CHART`——图表的数据点文本框能取到字，而图表内嵌的"编辑数据"工作表又被 `has_table` 当成普通表格捕获。
- **对策**（`1-parse_and_chunk.py`）：
  - CHART 形状整体跳过；
  - `_is_chart_data_table`：列数 ≥6 或数字单元格占比 >40% 判为图表数据表丢弃；
  - `_is_pure_number`：独立纯数字行单独跳过。
- **效果**：464 → 444 chunk，纯数字噪声块 38 → 2。

### 2. 表格空列与 CJK 断词
- **现象**：「华特迪士尼业务布局…幻灯片1」表格有一个整列空白。
- **根因**：该列是图片/logo 占位，python-pptx 取不到任何文字。
- **对策**：`sanitize_table_rows()` 统一清洗——单元格清洗、换行转空格、裁剪全空列、删全空行；`_fix_cjk_spaces` 移除两个汉字之间的空格（修"度 假村"）。

### 3. PDF 单行伪表格
- **现象**：「香港迪士尼乐园旅游攻略 > 第12页」表格只有一行（酒店名标题栏）。
- **根因**：PyMuPDF `find_tables` 把页面标题栏误判为表格，只有"表头"没有数据行。
- **对策**：清洗后 **仅 1 行且非空单元格 ≤2** 判为 degenerate 伪表格，`make_table_md` 返回空串；DOCX/PPTX 降级为普通段落保住文字，PDF 侧让 bbox 内文本自动回流普通文本路径。
- **后续又补了两类伪表**（`sanitize_table_rows` 返回四元组 rows/degenerate/giant/unbalanced）：
  - *giant*：数据行 ≤2 但单元格 >300 字（文本被装进单格表）→ 逐格降段落；
  - *unbalanced*：列填充率最高 ≥0.75 且次高 ≤0.5（SmartArt 经 COM 扁平化的标签-明细稀疏表，如"迪士尼公司结构.doc"23×2）→ 逐行降段落并横向去重。
- **全库标定**：其他文档 chunk 仅 ±1，零误伤。**启发式规则上线前必须全库扫描标定命中集合**，这条在噪声过滤上又救了一次（见三·8）。

### 4. 双栏 PDF 章节化（2026-06-10 那轮解析大改）
- **现象**：香港攻略双栏排版下 PyMuPDF blocks 全是碎片（页码/页眉/半句），p15 双栏正文被 `find_tables` 误判成 13×4 表，强制 flush 切断了内容流。
- **对策要点**：
  - `_is_pdf_footer` / `_strip_footer_lines`：行级剔除"返回目录我要纠错"、底部 12% 纯数字（混入正文同块也能剥）；
  - `_is_prose_mistable`：单元格 >60 字且含句号分号 → 双栏误判（全库仅 p15 命中，真表皇岗专线 maxcell=186 零误命中）；
  - `_collect_pdf_sections`：从页眉下方 45–140 的短标题 + 目录页条目构建章节词典；
  - chunker 新增 `kind=="section"`：章节边界 flush 且不带 overlap，防止跨章节串味；短块合并加 `_same_heading` 约束。
- **认知更新**：这套机制是"按文档章节/分区保留面包屑"，**不是抽取游玩路线顺序**——不要对切片层提出它解决不了的需求。源文件低质机翻（"广播罩""发育迟缓"）同理，切片层修不了。

### 5. 前端反斜杠路径（很隐蔽的前端坑）
- **现象**：知识库浏览灯箱退化为单图，图片 404。
- **根因**：`rel_path` 形如 `1-产品与服务详情\xxx.jpeg`，内联 `onclick="lbOpenAt('...\x...')"` 中 JS 单引号字符串把 `\x` 当未知转义吞掉，路径比较失败。
- **对策**：一律改 `data-rp` 属性 + `this.dataset.rp` 传值，缩略图和弹窗 img 都改。**任何把后端路径拼进内联 JS 字符串的写法都是地雷。**

### 6. bfcache 导致"改了没生效"错觉
重建索引后浏览器仍显示旧向量数（464/442），实则是 bfcache 旧页面。验证一律硬刷新（`?v=时间戳` / `?fresh=` 新 URL，browser_use 尤其爱复用旧标签），数据以 `/api/stats` 实时返回为准。

## 三、核心处理策略详解（重点：切片全流程）

> 本章按数据实际流过的顺序，记录每个环节"为什么这样设计、具体规则是什么"。代码对应 `1-parse_and_chunk.py`、`2-build_index.py`、`3-image_textify.py`、`lib/retriever.py`。

### 1. 全链路管线总览

```
0-转换旧格式.ps1        .doc/.ppt  --Word/PowerPoint COM--> converted/*.docx/.pptx + manifest.json
        │
1-parse_and_chunk.py    60 个文档 --结构感知解析+切片--> output/chunks.jsonl（文本块）
        │                                                              │
2-build_index.py        文本块 --text-embedding-v3(batch 8)--> embeddings.npy（断点续算）
                        faiss.IndexFlatIP(1152维, L2归一化) + bm25_index.pkl(char-bigram)
        │
3-image_textify.py      9 张图片 --RapidOCR + VL caption--> image_texts_<model>.json → 同库向量化
        │
前端 app.py / 4-evaluate.py / 5-diagnose.py  共用 lib/retriever.py 同一套检索逻辑
```

关键约定：
- **入口顺序固定**：0 转换 → 1 解析切片 → 3 图片文本化 → 2 建索引 → 前端/评估（3 与 1 可并行，但 2 必须最后跑）；
- 知识库 69 个文件：34 docx / 13 doc / 4 pptx / 5 ppt / 4 pdf / 9 jpeg，5 个分类文件夹；
- 最终库 472 文本块 + 9 图片向量，dim=1152。

### 2. 切片的总原则（先于一切规则）

1. **语义边界优先，800 字只是预算不是刀口**：以段落为最小聚合单位，绝不在句子中间硬切；只有单个段落本身超长才启用递归切分。
2. **结构信息必须保留并喂给检索**：标题路径（面包屑）拼进 embedding 正文首行；表格整块保留 Markdown 结构，不拍平成纯文本。
3. **内容降级而不是删除**：伪表格/图表表不直接丢，能转段落的转段落（唯一例外是 PPT CHART 形状——其文字纯是数据点/轴刻度，无阅读价值）。
4. **不可逆动作放到最后**：chunk id 在全部去重、合并、过滤完成后才顺序分配。
5. **启发式规则先全库标定再上线**：每条规则都要能列出全库命中清单和误伤清单（见三·8）。

参数：`CHUNK_SIZE=800`、`CHUNK_OVERLAP=120`、`SHORT_MERGE_LEN=100`、`MAX_MERGED_LEN=1200`、`MIN_CHUNK=8`。

### 3. 统一中间表示：block 流

三种文档格式（docx/pptx/pdf）解析后都输出同一种 block 序列，Chunker 只认 block，格式差异在解析器内消化：

| kind | 含义 | 携带字段 | 对切片器的作用 |
|---|---|---|---|
| `h` | 标题 | level(1-9)、text | 维护标题栈/面包屑，自身不产生 chunk |
| `p` | 普通段落 | text | 进缓冲聚合，或超限时硬切 |
| `table` | 整块 Markdown 表 | text | 强制 flush 后独立成块，永不与正文混 |
| `section` | PDF 语义章节 | text | flush + **无重叠**换章 + 弹栈到 level<2 |
| `boundary` | PPT 换幻灯片 | — | flush + 标题栈重置为文档名 |

### 4. 三类文档的解析策略

**DOCX（[1-parse_and_chunk.py:256](../1-parse_and_chunk.py#L256)）**
- 按 `doc.element.body.iterchildren()` **顺文档物理顺序**遍历，用 element→对象的两个 map 区分段落与表格——不能分别取 `doc.paragraphs` / `doc.tables`，那样会丢掉表格与段落的相对顺序；
- 标题级别三级兜底：样式名含 `Heading/标题` → 正则取数字 → 读 `outlineLvl+1` → 都没有按正文；
- 表格统一走 `table_to_blocks`（见三·6）。

**PPTX（[1-parse_and_chunk.py:349](../1-parse_and_chunk.py#L349)）**
- 每张幻灯片固定产出 `boundary + h1("幻灯片N：标题") + 内容 + 演讲者备注`，保证**一幻灯片一 chunk**（超长再递归切）；
- 组合形状（GROUP）递归展开 `_iter_shapes`；标题形状显式跳过，避免标题文字重复进正文；
- **CHART 形状整体跳过**；表格再过一遍 `_is_chart_data_table`（列数 ≥6 或非空单元格纯数字占比 >40%）双保险，拦住图表内嵌的"编辑数据"工作表；
- 文本框逐行处理：`join_vertical_text` 把连续单行单字（如"巍\n峨\n耸\n立"）合并，但保留 `·•◆■▪` 项目符号；独立纯数字行（轴刻度/数据点）丢弃，带文字的行保留；
- 备注以"演讲者备注："前缀保留。

**PDF（[1-parse_and_chunk.py:638](../1-parse_and_chunk.py#L638)）——最复杂，分四件事**
1. **先预扫描整本建章节词典**（`_collect_pdf_sections`）：
   - 来源一：页眉文档名块（y0<45）之后、高度 45–140 区间内的单行短标题（探险世界/住宿/乐园服务…），收集时跳过表格 bbox 防表头污染；
   - 来源二：目录页（前 1500 字命中"目录…content"）按 `/ ／ •` 和 2+ 空格切 2–10 字条目；数字开头的（价格项）、"目录/content"本身、带句读标点的一律不收；
2. **逐页分流**：去空白文本 ≥20 字走文本通道，否则判定疑似扫描页——且页内确有图像/绘图才调 OCR（dpi=200，RapidOCR 单例，按"normcase 绝对路径→页码"缓存到 ocr_cache.json，tmp+replace 原子写）；
3. **文本页表格与正文的合流**：`find_tables` 检出的表先按取整 bbox 去重，再过 `_is_prose_mistable`（存在 >60 字且含 `。；` 的单元格 → 双栏正文误判，全库仅 p15 命中，真表最长格 186 字但只有冒号逗号）；表格外文本块按"中心点落入表 bbox 且面积重叠 >30% 则跳过"排除后，与表块**统一按 y0 纵向排序**，恢复阅读顺序；
4. **噪声与章节分类**（`_classify_pdf_text`）：
   - 页脚："返回目录我要纠错"，或坐标模式下 y0>页高 88% 的纯数字页码；无坐标的拼接段按行剔除页码；
   - 页眉：y0<45 且等于文档名（或含前 4 字 name_key 且长度接近）；text 拼接模式则剥段首文档名行；
   - 章节标题：词典命中直接通过；否则形态启发——3–10 字、纯中英数字（允许·）、含中文、无标点、不含虚词表 `_TITLE_STOP_CHARS`（"的了在于和与…"），防止把半句正文当章节；
   - **坐标模式只认独立单行块**为 section，text 模式允许"首行标题+剩余正文"同段拆成 section+p；目录页不标 section（空标题无正文归属）；
   - 每页补一个 level=9 的 h"第N页"，页码因此进入面包屑但不干扰章节栈。

### 5. Chunker 状态机：block 流如何变成 chunk

核心是"**标题栈 + 累加缓冲**"的单遍状态机（[1-parse_and_chunk.py:808](../1-parse_and_chunk.py#L808)）：

- **面包屑**：栈内标题用 ` > ` 拼接（如 `香港迪士尼乐园旅游攻略 > 第12页 > 探险世界`），emit 时拼成 `面包屑\n正文` 作为 content——标题语义随每块一起进 embedding，显著提升主题相关性；
- **普通段落聚合**：段落不断 append 进 buf，`buf_len + 新段 > 800` 才 flush；
- **flush 的重叠（overlap）不是简单切 120 字**：取上一块正文尾部 120 字，在窗口内找最后一个 `。！；\n`，**从标点之后**开始作为下一块前缀，避免重复半句；
- **章节边界零重叠**：遇到 section 先 flush，再显式清空 buf——跨章节带 overlap 会串味（上一章尾巴粘到下一章）；
- **表格不进缓冲**：先 flush 正文，再逐片 emit；表格与正文之间、表格与表格之间永远不合并；
- **PPT boundary**：flush 后栈直接重置为文档名（幻灯片标题之间没有层级继承关系）；
- **超长段落 hard_split**：分隔符按语义强度降级 `\n → 。！？； → ". "（英文列表句号边界就是为公司结构英文列表加的）→ ，、 → 空格 → 字符硬切`；在 `[0.55×800, 800]` 窗口内找**最后一个**分隔符下刀，保证每片尽量长且边界自然；
- **超长表 split_long_table**：超 800 字才切；**每一组都重复表头两行**（没表头的数据行无法独立阅读）；按行攒组，组内还有超长行就扣除表头预算后 hard_split，每片照样补表头。

### 6. 表格处理统一管线（坑最密集的地方）

所有来源的表格都经过同一条管线 `sanitize_table_rows → 四元组判定 → 分流`：

**第一步：单元格级清洗**
- `clean`：`\xa0`→空格、`\x0b\x0c`（Office 软换行）→换行、去 `\r`；
- 单元格内换行转空格（表格单元格不该跨行）；
- `_fix_cjk_spaces`：**仅当空格两侧都是汉字才移除**（"度 假村"→"度假村"），"Disney 频道"这类中英文正常空格保留；
- 行宽不齐补空串对齐 → 删全空行 → 裁全空列（PPT 图片/logo 占位列）。

**第二步：稀疏列裁剪 `trim_sparse_cols`（≥4 行的表才参与，防误杀小表）**
- 列空值率 >80% 判稀疏；分三种情况精细处理，**没有一删了之**：
  - 仅表头有值（如票价表"立即预订"按钮列）→ 整列连表头删除；
  - 某行只有稀疏列有值（如时间表分组标题"与迪士尼朋友见面"）→ 文本提升到保留首列当标签行；
  - 数据行偶发稀疏值 → 并入该行末列，保留行归属（防御逻辑，当前库 0 命中）；
- 至少保留一列。

**第三步：四元组判质，决定表格的命运**
| 判定 | 条件 | 处理 |
|---|---|---|
| 正常表 | 其余全部 | 渲染 Markdown，整块保留 |
| `degenerate` | 清洗后仅 1 行且非空单元格 ≤2 | 单元格拼成**一个普通段落**（PDF 标题栏误判） |
| `giant` | 数据行 ≤2 且存在 >300 字巨型格 | 长格（>50字）各自成段，短格攒尾段（Word"文本容器"伪表） |
| `unbalanced` | 最高列填充率 ≥0.75 且次高 ≤0.5 | **逐行成段**：行内去横向重复文本（COM vMerge 合并单元格重复），首行若全同值或全是正文里出现过的主题词则丢弃表头 |

PDF 侧额外路径：被判伪表/双栏误判的表**根本不进 tboxes**，其 bbox 内文字自动回流普通文本块通道——同一份内容不需要在两条通道里做取舍。

### 7. 去重、短块合并与父子上下文

**emit 时的去重（跨文件级）**
- hash = `sha1(去全部空白后的 body)`——用 norm 而非原文，换行差异不影响判重；
- 命中已存在块时不新建，而是把当前来源 append 进该块的 `sources`（file/category/orig_format/chunk_seq/heading），实现"一份正文、多来源可溯"；全库 7 次重复命中。
- 非表格块 body <8 字直接丢弃（MIN_CHUNK，PPT 标题页"乐园"之类），表格不受限。

**finish 时的短块合并 v2（N4 定稿，只在单文档 doc_order 内进行）**
- 对象：非表格且 body<100 字；合并后总长 ≤1200；
- **优先后向并入前一块**，但必须同时满足：前块非表格 + `_same_heading`（两块 sources[0].heading 完全相同，防止跨章节乱拼）+ 总长不超限；
- 后向不可行（文档首块/前块是表格/会超长）→ 挂起为 pending，**尝试前向并入下一块**，约束相同；
- 下一块是表格或异标题 → pending 落地为独立短块（被表格夹住的短块只能保留）；
- 合并动作同步重算 hash、合并 sources、content 首行面包屑**保留目标块自己的**；
- 表格在任何方向上都不参与合并——这是 v1（短块并入表格制造半句 markdown 碎片）踩坑后加的硬约束。

**父子上下文（I1，生成侧用）**
- 合并全部完成后，按最终 doc_order 为每块拼 `parent_context = 上一块尾300字 + 本块 + 下一块头300字`；
- 线上 build_context 再对同源块做 suffix-prefix 重叠去重，避免喂给 LLM 的上下文大段重复。

**自动标签（M2）**：12 个主题（门票/退款/酒店/餐饮/邮轮/游乐项目/演艺/客诉/应急/会员/员工/攻略）用词库从"文件名+分类+面包屑"命中抽取，不引入任何外部资料。

### 8. 噪声过滤：为什么规则越收越窄

finish 阶段、合并之前先过 `_is_noise`。最初版本是宽正则，全库实测后发现合法内容被大面积误杀，最终定稿为**每条规则都带长度/上下文闸门**：

| 规则 | 闸门设计 | 全库实测命中 |
|---|---|---|
| "表格\n复制"导出占位 | 还要求总长 <80 | 少量 docx 导出残留 |
| 空表头碎片 | 仅含 `\|｜-—:：数字.` 且 <60 字 | 防御性 |
| 页脚模板 | 严格匹配"第X页(共/of)Y页" | 模板化文档 |
| `_is_empty_header` | ≤80 字且是"目录/版权/中文序号/纯标点"之一 | **0** |
| `_is_watermark_notice` | ≤120 字；命中 URL/©年份/版权词后，**剥掉通告片段剩余实质中英文字符 <12** 才算 | **0**（"上海迪士尼乐园©周边酒店"、CRM 内网 URL 均为合法内容，被闸门救下） |
| `_is_ocr_garbage` | 必须 ≥40 字，且中英数有效字符占比 <0.35 | **仅 id=46 一块** |

方法论：**先全库扫描统计候选命中，再按误伤反推阈值闸门**——0.35 这个数不是拍的，是全库标定到"只命中 1 块纯符号乱码、零误杀"的结果。

### 9. 图片文本化策略（3-image_textify.py）

- 9 张邮轮价格图双通道取文本：RapidOCR（图内文字/表格）+ qwen3.5-omni-flash VL caption（语义描述），合并后按普通文本块向量化入**同一个** faiss 库——图片因此可被"价格/航线"等文字问题直接检索到；
- 缓存指纹化：`image_texts_<safe_model>.json` + `__cache_meta__={caption_model, ts}`，换 caption 模型自动重算（旧版只按路径缓存，换模型后永不刷新）；
- 前端媒体匹配不看向量绝对阈值，而用 **gap rule（与候选图片的差距）+ 图片候选池内 BM25 最高分**校准（早期按全库 BM25 max 校准，图片 OCR 文本永远够不到阈值，图片永远不出现）。

### 10. 检索侧处理策略（lib/retriever.py，简述）

切片是"一次成型、长期复用"，检索是"每次查询实时跑的一条流水线"，顺序固定：

1. **召回（双路）**：向量 L2 归一化 + IndexFlatIP 余弦；BM25 字符 bigram（不依赖 jieba）。向量路 `vec_k=max(k×4,20)`，有类别预过滤时扩到 `max(k×6,40)` 保证过滤后取得满；类别过滤是**预过滤**（allowed_idxs）而非事后过滤；
2. **查询扩展**：DISNEY_DICT 同义词（上海迪士尼/达菲/FastPass 等）同时注入 embedding 输入和 BM25 查询；
3. **融合**：两路 RRF 等权 `1/(60+rank+1)`，融合池取 rerank_topn（约 12 条）；多意图时各子问题的两路结果进**同一个 RRF 池**累加，避免子问题各自截断互相挤占；
4. **R4 预过滤**：body<8 字的非表格块剔除；不足 k 时从向量序回填；
5. **Rerank 链**：rerank-v3.5（Cohere，AGICTO）→ qwen3-rerank（AGICTO→百炼），百炼自动排除 Cohere 模型；确定性失败码（401/403/404/欠费）立即 break 不重试；**返回空结果也按失败降级计数**，禁止静默空转；展示给用户的相似度始终用原始余弦（rerank 分不直观）；
6. **MMR（位次版，k≥3 才开）**：相关性项用池内位次线性衰减继承 rerank 序，多样性项才用向量余弦（旧版用原始余弦做相关性导致 -47.7pt，详见第五章）；
7. **同源限额 max_per_source=2**：超限时先跨源回填（从向量序找其他文件的块），全库都没有同源之外的候选才放宽限额；
8. **意图前置**：analyze_intent 判 underspecified 直接澄清短路；multi_intent 拆至多 4 个子问题走 search_multi，但 rerank 一律用**用户原始问题**（避免子问题语义偏移），MMR 用主意图向量；
9. **生成侧**：parent_context 拼上下文 + 强 system prompt（必须引用来源、禁止编造、表格用 Markdown）+ qwen-plus，流式 SSE，会话记忆保留最近 3 轮。

### 11. 切片策略设计取舍小结（可迁移的经验）

- **宁可块稍大，不可句被切断**：800 字预算 + 段落聚合 + 标点窗口，只有没办法才硬切；
- **结构是免费的高精度信号**：标题栈、PPT 幻灯片边界、PDF 章节词典、Markdown 表格，全部比"按长度乱切"值钱；
- **转换链路的产物不可信**：COM 扁平化会制造稀疏表/重复单元格，PyMuPDF 会误判标题栏和双栏——每个上游库的输出都要有"判质+降级"层；
- **同一份内容只保留一条通道**：PDF 伪表不进 tboxes 让文字回流，避免表格/文本重复入库；
- **所有启发式都要回答三个问题**：全库命中哪些？误伤哪些？阈值依据是什么？答不上来就不许进主线；
- **让下游的失效显性化**：chunk id 最后分配意味着重 parse 必重建索引+删 eval_qa_v2.json，这个约束写进记忆和文档，而不是靠人记住。

## 四、评估方法论类坑（本项目最值钱的教训）

这一组成连环坑，核心是一句话：**没有可信的评估，所有优化都是自我感觉良好。**

### 1. 指标污染：answer_hit 把 context 算进去了
- **现象**：答案侧命中率看着还行（0.225/0.250），但检索 Recall@5 已 0.900 近饱和，二者矛盾。
- **根因**：E1 v1 的 answer_hit 在"答案 + 上下文"拼串里数金标关键词，检索到了就算答对，生成质量被注水。
- **对策**：E1 v2 strict——只在 ANSWER 内数金标；同时报三个数拆开看：
  - `evidence_coverage`（证据有没有召回）
  - `answer_hit`（答案有没有命中）
  - `answer_hit_given_evidence`（证据在的条件下答对率，**才是真正的生成侧指标**）
- **教训**：指标分母/统计范围要先审，再看数值。

### 2. 多因子同改，无法归因（0.895→0.407 之谜）
- **现象**：线上口径（k=3 + 限额2 + MMR + Rerank）Recall 只有 0.407，而混合+Rerank 有 0.895，落差巨大却拆不开。
- **对策**：加消融档「混合+Rerank(k=3，无限额、无 MMR)」，用单因素对照隔离后处理。
- 同期还枪毙了两个伪优化：
  - 动态限额公式 `min(k-1, MAX_PER_SOURCE)`：k=3 时与原值完全相同，等于没改；
  - 凭 n=80 的小样本调 MMR λ：差异在噪声范围内，属于过拟合调参。
- **方法论**：优化目标从 Recall@k 切换为端到端 answer_hit——**检索指标可能与答案指标反向优化**。

### 3. ★ 最大的坑：对照配置与线上不一致，决策证据不成立
- **事实**：当时据一份 k 值对照数据得出"k=3 相关决策"，但审核（四线交叉：脚本→产物→缓存→日志）发现那份产物的配置是 `use_rerank=true, use_mmr=false, max_per_source=null`——**纯 Rerank、关 MMR、无限额**。
- **问题**：拿"关 MMR"条件下测得的 k 值差异，去决策"开 MMR"的线上档位，判据无效。
- **对策**：
  - 必须有一个**与线上逐字同配置**的评估档（top_k=5 + 修复后 MMR + 限额实际值）；
  - 补 **2×2 对照** `{k=3, k=5} × {MMR 开, MMR 关}`，才能分离 k 与 MMR 的净贡献。
- **反思**：做实验时先写下"这个档对应线上哪个开关组合"，label 与参数必须同源，否则数字再漂亮也不能用于决策。

### 4. ★ 主评估早于代码修复：整批落盘数值失效
- **时间线证据**：
  - 01:51 `eval_results.json` 写出（主评估结束）；
  - 02:16 `retriever.py` MMR 修复落盘；
  - → 主评估数值全部是**修复前口径**，但仍在被当作现状引用。
- **对策（机制化，不靠人记）**：
  - 索引指纹：评估产物头部固化 `index_md5`（当时 bec42e97ca01）；
  - 启动守护：评估脚本启动时校验 index_md5，不一致拒绝复用旧结果；
  - 时间线意识：审核任何数值前先对 mtime——**产物时间早于代码修复时间 = 废纸**。

### 5. ★ "无源产物"：诊断脚本没入库
- **事实**：diag_pool / diag_mmr_fix / diag_answer_k 三个 json 在全仓库 `.py/.md` 中零引用，由仓库外临时脚本生成，无法复现、无法审计、无法回归。
- **对策**：固化为 `5-diagnose.py`，产物头部写全元数据 `{model, k, use_mmr, mmr_lambda, max_per_source, index_md5, gen_ts}`。
- **教训**：**任何影响决策的数据，生成它的代码必须在仓库里。** 临时脚本跑完即弃 = 证据链断裂。这次的审核报告（output/本轮改动落地审核报告.md）本身就是因为"口述烟测、无留痕"才被要求做只读审计。

### 6. 缓存指纹不全 → 串味与永不重算
- **eval_ans_cache**：旧键是 `sha1(模型|prompt版本|问题|上下文)`，不含 k/MMR/索引指纹，仅靠上下文间接区分，脆弱 → 键补齐 k / MMR / 索引指纹。改生成 prompt 要 bump `_ANS_PROMPT_VER`。
- **image_texts**：旧缓存只按 rel path，无模型戳，换 caption 模型后旧产物永不重算 → 文件名指纹化 `image_texts_<model>.json` + `__cache_meta__={caption_model, ts}`，build 侧优先指纹文件、回退旧版。
- **通用原则**：缓存键 = 全部影响输出的因子；换 embedding 模型还必须删 embeddings.npy + .faiss 重建（维度/空间都变了）。

### 7. 其他评估小坑清单
- `MMR_LAMBDA=0.0` 被当成 falsy 回退默认 0.72 → `lam=0.72 if mmr_lambda is None else mmr_lambda`（判 None 不判假值）；
- 报告硬编码 Recall@5，非 k=5 档指标误导 → 动态显示 Recall@{k}；
- 硬编码 1152 维 → `settings.EMBEDDING_DIM`，build/eval 两侧 assert 实际 shape；
- 中文意图标签未归一化（LLM 回显"信息不足型"）→ `_normalize_type` 别名映射 + 混写括号提取，只保留合法枚举；澄清路径不受影响，但非澄清的中文标签以前会**漏改写**；
- 噪声过滤宽正则误杀合法内容：全库 455 块实测，空标题 0、真水印 0（`©` 命中的是"上海迪士尼乐园©周边酒店"，URL 是 CRM 手册合法内网地址），仅 1 块 OCR 乱码（id=46）→ 收窄为三条精判（`_is_empty_header` 防御 / `_is_watermark_notice` 短块≤120且去通告后实质字符<12 / `_is_ocr_garbage` ≥40字且有效字符占比<0.35）。**不要拍脑袋上宽正则，先全库标定。**

### 8. ★ 评估工程提速：并行化、缓存与重复消除（实现细节）

80 题 × 多档位的评估矩阵，串行跑一轮是几十分钟级。优化后所有档位共用同一套并发与缓存基础设施（`4-evaluate.py`），细节如下：

**① 线程池并发（EVAL_WORKERS=8）**
- 通用执行框架 `_run_concurrent(work_items, workers, ...)`（[4-evaluate.py](../4-evaluate.py)）：`ThreadPoolExecutor` 提交全部任务，`as_completed` 收割，**按下标保序返回结果列表**（并发不乱序，报告行序稳定）；每完成 10 题触发一次 `checkpoint()` 把缓存落盘 + `on_done` 进度回调；
- 检索侧、答案侧、意图评测（`evaluate_intents`/`evaluate_intent_gold`）全部走这一个框架；
- **检索+生成在同一个 worker 内完成**——不把"先并发检索、再并发生成"拆两段，省掉中间结果汇集和第二轮排队。

**② embedding 串行预热，避开并发写缓存**
- 提交线程池**之前**，主线程先把 80 个 query 的向量逐个算进 `vec_cache`（[4-evaluate.py](../4-evaluate.py)）——`vec_cache` 是普通 dict 非线程安全，并发首次写入有竞态；预热后 worker 内全部命中只读；
- `vec_cache` **跨配置档位复用**：换 k/MMR/限额档位不重算 query 向量；
- 带改写的档位（use_rewrite=True）：改写串行执行（本身走磁盘缓存），再把全部子问题向量一并预热。

**③ OpenAI client 模块级单例**
- `_GEN_CLI` / `_QA_CLI` 全局单例（[4-evaluate.py](../4-evaluate.py)）：OpenAI 客户端内部持有 httpx 连接池，线程安全可共享；
- **旧实现每次调用新建客户端 → 320 次重复 TLS 握手，是主要耗时来源之一**。教训：SDK client 的默认姿势就是复用，"用完即建"在批量场景里是隐形税。

**④ 生成答案磁盘缓存（跨档去重的关键）**
- `eval_ans_cache.json`：key = `sha1(GEN_MODEL | _ANS_PROMPT_VER | index_md5 | k | use_mmr | λ | max_per_source | prompt_style | 问题 | 上下文)`（`_ans_cache_key` + `_ANS_SCOPE`，[4-evaluate.py](../4-evaluate.py)）；
- 效果：**不同档位检索到相同上下文时直接命中，不重复调 LLM**；整个评估矩阵跑完、改天重跑也是零调用；
- **失败不缓存**（`_gen_answer_cached`，避免把一次限流/超时固化成永久坏答案）；
- 文件头 `__cache_meta__={gen_model, prompt_ver, index_md5}`，加载时任一不符**整份作废重建**——宁可重算，不可用错世界的缓存；
- `_ANS_PROMPT_VER = "v2"`：改生成 prompt 必须 bump 版本号，否则旧答案静默复用。

**⑤ 意图改写磁盘缓存（三处共用）**
- `eval_rewrite_cache.json`：key = `(模型, 阈值, query, history)`；"改写 query 检索档"、"意图评测"、"意图金标"三处共用同一份（[4-evaluate.py](../4-evaluate.py)），跨档跨运行零重复 LLM 调用，且结果可复现；
- `REWRITE_CACHE_VER = "v1"`：改 intent prompt 或标签归一化逻辑时 bump。

**⑥ 重复消除与杂项**
- 逐档核对参数时发现**两个答案档参数逐字相同**（纯重复劳动）→ 砍掉后生成调用从 320 次降到 240 次；
- 删掉每题 `sleep(0.2)` 的礼貌性节流——有了 429 重试退避（`_time.sleep(wait)` 指数退避）就够了，固定 sleep 是白送的耗时；
- 重试保留：LLM 调用失败按退避重试，但检索向量的 429 错误用独立短退避（0.5s）区分处理。

**⑦ QA 金标的指纹对齐（提速的配套前提）**
- 缓存/并行之所以能放心复用，是因为同源校验做在了前面：每条 QA 携带 `chunk_hash`（切片阶段 sha1），`load_or_build_qa` 按 `born_index_md5` → 当前 `index_md5` 用 chunk_hash **重映射金标**，记录 kept/missing 并写 remap_history；索引换了、hash 对不上的条目显式报 missing，而不是静默错位；
- 评估启动时校验旧 `eval_results.json` 的 `index_md5`，不一致拒绝复用（[4-evaluate.py](../4-evaluate.py)）——这就是四·4"数值失效"坑的机制化修复。

**可迁移经验**：批量 LLM 任务的提速三板斧——**连接池单例（省 TLS）、磁盘缓存 key 含全部影响因子（省重复调用）、线程池 + 保序收割（省墙钟时间）**；而一切复用的前提是**指纹同源校验**，否则提速只是更快地产生错误数据。

## 五、★ 标杆案例：MMR 性能暴跌的根因排查（完整流程复盘）

这是本轮最值得复刻的排查过程。特点：**没有急着调参，先用打点证伪假设，再用单因素消融锁定因子，最后读算法定位根因。**

### 第 0 步：立规矩
用户明确指示：**先查候选池，再动 λ。** 事后看这句话直接避免了一整晚的无效调参。

### 第 1 步：分段打点，证伪"阈值砍池"假设
- 在 `retriever.search` 各阶段加 POOL_STATS（`_STATS_LOCK` 保护）：
  `rrf_out=12 → after_r4=12 → rerank_out=12 → mmr_in=12 → final=5`
- 结论：**候选池全程无裁剪**，后处理拿到的就是完整 12 池。同时确认 `MEDIA_SIM_THRESHOLD` 只用于图片媒体卡匹配，不在文本管线——"阈值把候选砍没了"的假设被证伪。

### 第 2 步：单因素消融，锁定肇事者（k=5, n=86）
| 档位 | Recall@5 | 相对无后处理 |
|---|---|---|
| A 无后处理 | 0.884 | — |
| B1 仅 MMR | **0.407** | **-47.7pt，独自造成全部损失** |
| B2 仅限额2 | 0.860 | -2.4pt（噪声级） |
| C MMR+限额 | 0.419 | ≈ B1 |

→ 与 k 值、限额无关，**MMR 是唯一主因**。

### 第 3 步：读算法，找到根因
旧 `_mmr_select` 的相关性项用**原始向量余弦** `vecs @ q`：
- 在当时 1152 维新空间下，纯向量 recall 仅 0.558；
- 等于把 Cohere rerank 辛苦排出的 12 池顺序**整体丢弃**，退回最弱的纯向量信号；
- 所以 **λ→1 也只能回到纯向量水平，调 λ 在数学上就无解**——这解释了为什么 λ 扫 0.72/0.55 全都差。

### 第 4 步：修复（`lib/retriever.py:776`）
相关性项改为**池内位次线性衰减** `rel=(n-j)/n`，继承 rerank/RRF 的排序信号；多样性项仍用向量余弦。

### 第 5 步：同参数对照验证（diag_mmr_fix.json）
| 档 | 修复前 | 修复后 |
|---|---|---|
| MMR λ0.72 | 0.407 | **0.884**（与无后处理持平）|
| MMR λ0.55 | — | 0.872 |
| MMR + 限额2 | 0.419 / MRR 0.329 | **0.860 / 0.770（+44pt）** |

最终候选线上口径：k=5 + 限额2 + 修复 MMR λ0.72 = 0.860，多样性的诚实代价仅 -2.4pt。

### 这个案例的可复用 SOP
1. **先立"不准调参"的规矩**，直到打点证明参数所在环节真的有问题；
2. **沿管线分段打点**，把损耗定位到具体两个阶段之间；
3. **主动证伪自己最顺手的假设**（本例是阈值砍池）；
4. **单因素消融**，一次只开一个开关；
5. **读公式**，想清楚每个输入信号来自哪里、有没有把更强的上游信号丢掉；
6. 修复后用**完全相同参数**对照，并在真实服务重启 + 烟测收尾（本例：5 块/3 来源、rerank Cohere 主链零降级）。

## 六、线上事故类坑

### 1. AGICTO 全站欠费：HTTP 200 包着错误信封
- **现象**：查询 500，health 正常、索引正常；前端只显示"流式请求失败 500"。
- **根因链**：AGICTO 对 rerank 和 embedding 都返回 HTTP200 + `error.code=insufficient_quota`；rerank 链按预期降级到百炼 qwen3-rerank（fallbacks=1），但 `get_text_embedding` 不识别该信封，拿到 `embs=None` 后继续跑 → TypeError 500。
- **对策**：
  - `_AGICTO_ERR_HINTS`：错误码稳定映射（insufficient_quota / invalid_api_key / model_not_found），原始 message 作明细；
  - 取不到 embs 直接抛显式 RuntimeError，不许 None 往下游流；
  - SSE 路径在 `!resp.ok` 时读取 JSON error 体——实测红气泡显示"AGICTO 账户余额不足，请前往平台充值…"。
- **通用教训**：**OpenAI 兼容网关会用 200 包业务错误，不能只判 HTTP 状态码**；错误信息要一路透传到用户看得见的地方。
- **附带优化**：rerank 确定性失败码（401/403/404 + insufficient_quota / Not enough money）立即 break 降级不重试，欠费时省掉每级 2 次指数退避约 6 秒。

### 2. 模型/平台兼容
- tongyi-embedding-vision-plus 在 AGICTO `/v1/embeddings` 报 IllegalInput → 换 text-embedding-v3（1024/1152 维，换模型必须删 embeddings.npy + .faiss）；
- rerank 主链多次调整，最终定稿 AGICTO `rerank-v3.5（Cohere）→ qwen3-rerank`，百炼兜底自动过滤 Cohere 模型；模型名变动要同步 settings 默认值、.env、README、docstring，否则就是口径漂移。

## 八、排查流程通用 SOP（沉淀下来的方法论）

### A. 效果异常（检索/答案变差）
1. **对时间线**：产物 mtime vs 代码修复 mtime，先确认手上的数是不是旧世界的；
2. **查指纹**：index_md5 / 缓存键 / 模型戳，确认数据与当前代码同源；
3. **分段打点**：沿管线记录每阶段候选数与分数，把损耗夹逼到两阶段之间；
4. **单因素消融**：一次一个开关，必要时 2×2；
5. **读公式/读信号流向**：确认强上游信号有没有被弱信号覆盖（MMR 案）；
6. **同参数对照验证修复**，再重启真实服务烟测；
7. 样本小（n≈80）时不报小数点后第三位的差异，参数结论标注噪声范围。

### B. 切片异常（某个 chunk 内容不对）
1. 从**具体异常 chunk 的面包屑**反推源文件页/幻灯片；
2. 判断走的是哪条解析分支（表格 / 文本块 / OCR / CHART / COM 扁平化）；
3. 启发式规则修改前，**全库扫描标定命中集合**，列出误伤清单；
4. 重建索引 → 删 eval_qa_v2.json → 浏览器硬刷验证；
5. 记录 chunk 总数变化（464→444→433、433→472），数量突变要能解释每一块去向。

### C. 线上报错
1. 先看 `/api/health`（降级数、缓存、会话），区分检索链与生成链；
2. 抓包看 HTTP 状态码**和信封体**（200 也可能是错误）；
3. 确认是哪个平台/哪级模型、key 与余额；
4. 确认跑服务的解释器和端口占用进程（别让全局 Python 旧进程背锅）。

### D. 改动审核（自查或他查）
四线交叉：**脚本（代码在不在仓库）→ 产物（配置/指纹/时间戳）→ 缓存（键是否含全部因子）→ 日志（有没有真实运行痕迹）**。本次审核报告即按此框架执行，三项硬问题（证据不成立、数值失效、无源产物）全部是靠交叉比对发现的，而非看结论本身。

## 十一、新增踩坑与结论（2026-10-20 ~ 10-22，S1–S8 两轮工程优化期）

> 第 1~10 章覆盖 2026-10-02 及以前；本章记录 S1–S8 工程优化期（2026-10-20 ~ 10-22）新增的坑。
> S1–S8 各阶段内容与进度总表见 `02-全流程细节梳理-迪士尼RAG助手.md` 第 17 章。

### 1. ★ 评估长跑被上游 503 污染而不自知（本期最值钱的新教训）

**现象**：S1–S6 收官重跑期间，rerank 上游 AGICTO 间歇性 503，降级链静默兜底——档位读数**保守下偏但汇总行完全看不出来**（一次 436 次降级、一次合跑网格 31 次波及 7 档）。
**根因**：rerank 失败走降级链是正确设计，但"降级了多少次"如果只看结尾汇总，无法归因到具体档位；被污染的档位与干净档位混在一份结果里。
**对策（已固化为机制）**：
1. 每个结果行记录该档 rerank 降级数，**按结果行切分日志逐档归因**，不看汇总行下结论；
2. 干净重跑脚本（`15-rerun_polluted_tiers.py` / `18-rerun_polluted_grid.py`）带安全闸门：**仅首选 rerank 零降级（fallbacks=0）才写回**，幂等可重跑；
3. 瞬时失败重试升级为指数退避 + **full-jitter**（`RERANK_MAX_RETRY=5`）——固定退避在多线程下会同步重试、再同步撞上同一个 burst（实测每档稳定 5-7 次扛不过），抖动后才能错峰穿过。
**可迁移**：任何"有降级链的长跑评测"，都必须把降级计数做成结果行的一等字段，否则干净与污染数据无法分离。

### 2. 同步重试撞 burst：退避必须加抖动

多线程（`EVAL_WORKERS=8`）下固定退避（sleep 1s/2s）会让 8 个线程同时失败、同时重试、同时再撞上游同一个 503 窗口。full-jitter（sleep ∈ [0, base·2^attempt]）后实测可穿窗。意图链路同款（`INTENT_BACKOFF_BASE=0.8` + jitter）。

### 3. 假进度比没有进度更糟

前端原先用定时器猜"检索中→重排中→生成中"，与实际阶段无关——排障时"显示检索中其实卡在 rerank 欠费等待"，误导方向。改为**后端真实阶段边界**：检索管线在独立工作线程执行，真正发起 LLM/embedding/rerank 调用前才经队列推送 stage 事件（rewrite→embed→retrieve→rerank→generate），rerank 降级/失败也作为 stage detail 真实呈现。工作人员面板看到的每个阶段都可信。

### 4. 意图客户端每次调用新建：连接池不复用是超时爆发首因

旧实现每次 LLM 调用新建 OpenAI client，意图链路一次问答最多 6 次调用 = 每问重建 6 条 TCP+TLS。135 条金标实测：18% 的"需改写题"因 `Request timed out` 被静默降级为原 query 检索（multi_acc / type_hit / term_keep 三项同时塌陷）。改为模块级单例 `_INTENT_CLI`（httpx 连接池线程安全可共享）后解决。**教训：SDK 客户端是连接池载体，不是一次性工具。**

### 5. ★ 文档与代码分叉，比代码分叉更隐蔽（2026-10-22 独立审核发现）

**现象**：代码是对的，但整套文档/配置模板指向已停更的 7- 版本——README 11 处命令路径与目录树根写 `7-完整知识库版本\`、requirements.txt 标题与安装命令、app.py docstring 启动命令全是 7-；`0-转换旧格式.ps1` 输出目录硬编码到 7- 的 converted/（在 8- 里跑会把产物写进 7-）；`ROOT7` 变量名实际指向版本根目录（名字误导）；`.env.example` 比 `settings.py` 少整整一代参数（14 个）；README 里 `RERANK_BACKOFF_BASE=2.0` 与代码默认 1.0 自相矛盾。
**为什么比代码分叉更危险**：代码分叉有测试/基线兜底，文档分叉直接骗人——新人照 README 操作就会装错版本、跑错目录、漏配参数，且**没有任何自动化会报错**。
**对策**：文档路径体系统一到活跃版本；配置模板与 settings.py 逐参数对齐；命名去版本残留（ROOT7→VERSION_ROOT）；README 数值与代码默认值核对。**纪律：每次代码大版本变迁，文档清单要作为交付物的一部分过一遍，不能假设"文档会自己跟上"。**

### 6. 评估答案档未设 temperature → ±3.8pt 生成噪声

线上/评估全仓零 `temperature` 设置，同上下文重生成答案 100% 漂移（72 题实测），5 题 hit 翻转——`answer_hit_given_evidence` 0.791→0.767 无法用回归解释（两比例 z=-0.441 不显著；8 个 hit→miss 中 7 例 top-3 上下文不变），最终判定为生成采样噪声。**代价**：答案档测量精度 SE≈±3.8pt（n≈115），小于该幅度的"提升"不可信。**候选对策**：评估侧设 `temperature=0` 使基线可复现（会改口径，需重跑 183 基线对比后才能引用新旧读数——已列为方向 7，未拍板）。

### 7. 被打断轮次的"编辑落盘核查"法

多步编辑被用户中断后，**不能假设**中断点之前的编辑都已落盘/都没落盘——必须逐项 grep 实证。实例：某轮 settings + import 已落盘、主体函数未落盘；某轮 Edit 因旧文本已被前序改动而失败（`sess_prune` 已被加锁包装）。**纪律：中断恢复后第一步永远是核查实际落盘状态，再决定补什么。**

### 8. 限流键信任 X-Forwarded-For + TTL 清理依赖访客行为

- `X-Forwarded-For` 完全由客户端可控，拿它当限流键等于把限流开关交给请求方（伪造轮换头即可绕过）；本服务绑 127.0.0.1 实践风险低，仍修正为 `remote_addr` 优先。
- `sess_prune` 原先只在 `/api/session/new` 时触发、限流桶只在同一 IP 再次请求时才清过期项——不常来的 IP/会话常驻内存。已加 5 分钟周期维护 daemon 统一清扫。

### 9. 本期新增"最佳实践"清单（与第 7 章工程纪律合并执行）

1. **fail-fast 前置**：密钥缺失在启动即报错（`require_keys`），不到运行期才晦涩失败；但要有选择地 fail-fast（rerank Key 缺失仅告警——避免误伤 `use_rerank=False` 场景）；
2. **降级必须记账**：rerank（calls/fallbacks/circuit_skips）、意图（degraded_by 分桶）、自检（evidence_check_failed）——静默降级只能事后从指标塌陷反推；
3. **指纹三段式**：金标↔索引（chunk_hash remap）、产物↔索引（index_md5）、缓存↔口径（模型+dim+prompt 哈希）——口径一变自动失效，杜绝"旧缓存冒充新结论"；
4. **200 也要查信封体**：HTTP 200 包着错误信封（欠费）比 4xx 更危险，因为它看起来成功；
5. **负结果也要写成文档**：S3 自检 A/B 不达标 → 维持默认关并留档；"我们试过 X 且证明不行"和"我们做了 Y"同样有价值；
6. **先审核后落地**：触及检索/索引主线的改动，用户审核通过前不落地（本轮全部遵守）。
