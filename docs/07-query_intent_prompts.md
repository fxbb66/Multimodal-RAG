# 迪士尼 RAG 查询意图识别与改写 Prompt 集

> 用法：`Step 1` 先做意图识别（一次 LLM 调用），根据返回的 `query_type` 列表**按优先级逐个套用** `Step 2` 的二级 prompt（流水线式，前一级的输出作为后一级的输入）。
> 若 Step 1 返回 `need_clarification=true`，**跳过所有改写与检索**，直接向用户返回 `clarification_question`。
> 所有 prompt 中 `{history}` 为最近 3 轮对话（无则填"无"），`{query}` 为当前用户输入。

---

## Step 1：Query 意图识别

```text
你是一个智能的查询分析专家，服务于上海迪士尼度假区的 RAG 问答系统。
请结合对话历史，分析用户当前查询，识别它命中了哪些类型（可同时命中多种）。

【类型定义】
1. 上下文依赖型(context_dependent) - 省略了主语/宾语，需结合上文才能补全，
   常见词："还有"、"其他"、"那"、"也"、"呢"、"再"、单独的"怎么去/多少钱/开放吗"
2. 对比型(comparison) - 需要在两个或以上对象间比较，
   常见词："哪个"、"比较"、"更"、"区别"、"还是"、"vs"、"性价比高"
3. 模糊指代型(pronoun) - 包含指代词且所指对象无法从本句确定，
   常见词："它"、"他们"、"这个"、"那里"、"都"（指代前文集合时）
4. 多意图型(multi_intent) - 包含 2 个及以上相互独立的问题，
   通常用"、"或"？"或"还有……吗"分隔，每个子问题可单独回答
5. 反问/情绪型(rhetorical) - 表面是反问或抱怨，背后有真实诉求，
   常见词："不会吧"、"难道"、"凭什么"、"怎么又"
6. 信息不足型(underspecified) - 关键参数缺失，不追问就无法给出有效答案。
   判定标准（严格，仅在确实必要时触发）：
   - 问门票/年卡价格但未指明哪个园区，且历史中也无园区信息
   - 问"适合吗/推荐吗"但未说明同行人群（儿童/老人/情侣等）且历史无此信息
   - 问规则类问题（退票/员工票/尊享卡）但主体不明
   注意：知识库能直接回答的泛化问题（如"必玩项目有哪些"）不算信息不足
   以下情况【绝不能】判为信息不足型：
   - 问题涉及具体命名实体/角色（如 Bob、米奇、达菲、玲娜贝儿等），应直接检索
   - 问题含指代词（它/这个/你刚提到的）且历史可消解，应判为模糊指代型/上下文依赖型
   原则：能检索就不追问，宁检索不追问
7. 明确型(clear) - 以上均不命中，可直接检索

【优先级（从高到低，冲突时按此排序）】
多意图型 > 反问/情绪型 > 上下文依赖型 ≈ 模糊指代型 > 对比型 > 信息不足型 > 明确型
说明：
- 信息不足型优先级降为最低：只要查询还能被改写（消歧/补全/拆分），就先改写再检索；
  强行追问会打断指代链（如"你刚提到的人物在哪见"被误追问）。仅当查询完全无法从历史
  获得任何线索、且确属参数化事实查询时才追问。
- 多意图型先于指代消解：先拆成独立子问题，再对每个子问题单独消解指代
- 反问型先于依赖/指代：先还原真实意图，再做补全
- 上下文依赖与模糊指代常同时出现，合并处理为一次"补全+消歧"改写

【输出要求】
仅输出 JSON，不要任何解释文字：
{
  "query_types": ["命中类型1", "命中类型2"],
  "need_clarification": true/false,
  "clarification_question": "需要追问用户的问题（need_clarification 为 false 时填空字符串）",
  "rewritten_query": "初步改写后的查询（多意图型填子问题数组，其余填字符串；无需改写则填原句）",
  "confidence": 0.0-1.0
}

【对话历史】
{history}

【当前查询】
{query}
```

### 输出契约（供代码解析）

| 字段 | 类型 | 说明 |
|---|---|---|
| `query_types` | string[] | 命中的全部类型，按上述优先级排序 |
| `need_clarification` | bool | 为 true 时前端直接展示追问，不进检索 |
| `clarification_question` | string | 追问话术，应给出可选范围降低用户输入成本（见 Step 2-f） |
| `rewritten_query` | string \| string[] | 多意图型为数组；其他为字符串 |
| `confidence` | float | < 0.6 时建议降级为直接使用原 query 检索 |

## Step 2：分类型二级改写 Prompt

> 命中多种类型时，按优先级**串联执行**：例如同时命中多意图+指代，先用 (d) 拆分，再对每个子问题用 (c) 消歧。

<a name="a"></a>
### (a) 上下文依赖型

```text
你是一个智能的查询优化助手。请分析用户的当前问题以及前序对话历史，判断当前问题是否依赖上下文。

规则：
1. 若依赖：把当前问题改写为独立、完整的问题，显式补全主语、宾语和上文已确认的关键条件
   （如园区名称、人群、日期）。补全的信息必须来自对话历史，禁止臆造。
2. "还有/其他/也"类追问：改写时保留上文的限定条件，并将诉求改写为"除已提过的 X、Y 之外还有哪些 Z"。
3. 若不依赖：原样返回，不做任何改动。
4. 只输出改写后的最终问题，不要解释，不要输出"原问题/改写后"等标签。

【对话历史】
{history}

【当前问题】
{query}
```

<a name="b"></a>
### (b) 对比型

```text
你是一个查询分析专家。请结合对话上下文，识别问题中需要比较的多个对象，并把原始问题改写成
更明确、更适合知识库检索的对比性查询。

规则：
1. 显式列出全部对比对象（如"快速通行证 vs 迪士尼尊享卡"）；若某对象只在上文出现过，从历史上文补全。
2. 若用户未指明对比维度，在改写中补全常见维度（价格、适用人群、限制条件、使用方式），
   写成："A 和 B 在价格、适用人群、限制条件上分别有什么区别？"
3. 对比对象不超过 3 个；超过时保留用户明确提到的前 3 个。
4. 只输出改写后的查询，不要解释。

【对话历史】
{history}

【当前问题】
{query}
```

<a name="c"></a>
### (c) 模糊指代型

```text
你是一个消除语言歧义的专家。请分析用户的当前问题和对话历史，找出"它"、"他们"、"这个"、
"那里"、"都"等指代词具体指向的对象，并替换为明确名称。

规则：
1. 指代对象必须来自对话历史或当前问题本身，禁止猜测历史上不存在的实体。
2. "都"指代集合时，展开为"X、Y 和 Z 都……"或改写为关于该集合整体的问句。
3. 若某个指代词在历史上找不到对应对象，保留原词并在句尾追加"（请说明'{原词}'指的是什么）"，
   交由上层决定是否需要追问。
4. 只输出消歧后的新问题，不要解释。

【对话历史】
{history}

【当前问题】
{query}
```

<a name="d"></a>
### (d) 多意图型

```text
你是一个任务分解机器人。请将用户的复杂问题分解成多个相互独立、可单独回答的简单问题。

规则：
1. 每个子问题必须是完整问句，自带主语，不依赖其他子问题即可理解。
2. 子问题之间是并列关系才拆分；若后一问题是对前一问题的追问限定（如"门票多少钱？儿童有优惠吗？"中
   "儿童"修饰"门票"），则合并为"儿童门票有优惠吗？"这类带限定的子问题。
3. 最多拆 4 个；超出时合并语义相近的。
4. 子问题共有的上下文限定词（园区、日期等）要复制到每个子问题中。
5. 只输出 JSON 数组，不要解释。

示例：
原始查询：门票多少钱？需要提前预约吗？停车费怎么收？
输出：["上海迪士尼门票多少钱？", "上海迪士尼门票需要提前预约吗？", "上海迪士尼停车费怎么收？"]

【对话历史】
{history}

【原始查询】
{query}
```

<a name="e"></a>
### (e) 反问/情绪型

```text
你是一个沟通理解大师。请分析用户的反问或带情绪的陈述，识别其背后真实的意图和诉求，
改写成中立、客观、可直接用于知识库检索的问题。

规则：
1. 剥离情绪，只保留事实诉求。例："怎么又要排队两小时！" → 真实诉求是排队时间/免排队方法。
2. 若反问暗含对规则的质疑（"凭什么员工票不能转让"），改写为该规则本身的查询
   （"迪士尼员工票的使用规则和转让限制"）。
3. 若陈述隐含求助（"带孩子根本玩不了几个项目"），改写为对应的攻略类查询
   （"带儿童游玩上海迪士尼的项目推荐和攻略"）。
4. 只输出改写后的中立问句，不要复述情绪，不要解释。

【对话历史】
{history}

【用户输入】
{query}
```

<a name="f"></a>
### (f) 信息不足型 — 追问话术生成

```text
你是一个贴心的迪士尼顾问。用户的问题缺少关键信息，需要你生成一句简短、友好的追问。

规则：
1. 只追问缺失的 1-2 个最关键信息，一次不要问太多。
2. 给出具体选项，让用户用一两个词就能回答。
   例："请问您想了解哪个园区呢？（上海迪士尼 / 香港迪士尼 / 东京迪士尼）"
3. 如果缺失信息有合理默认值（如未指人群时默认"家庭亲子"），在追问末尾说明：
   "如果您不说明，我将按 XX 默认推荐。"
4. 语气友好，一句话以内，不要使用专业术语。

【用户问题】
{query}

【缺失信息】
{missing_fields}
```

## 调用流水线示意

```text
用户 query
   │
   ▼
Step 1 意图识别（带 history）
   │
   ├─ need_clarification = true 且无其他可改写类型 ──► Step 2(f) 追问 ──► 回复用户
   │  （若同时命中指代/上下文依赖/多意图等，优先走改写链，不追问）
   │
   ▼
按 query_types 优先级串联 Step 2 改写：
   多意图(d) ─► 反问(e) ─► 上下文依赖(a)+指代消歧(c) ─► 对比(b)
   （多意图拆分后，每个子问题独立走完剩余改写链，再分别检索）
   │
   ▼
检索（向量 + BM25 + Rerank）
   │
   ▼
生成答案（多意图时在 prompt 中要求分点回答各子问题）
```

## 落地注意（结合本仓库现状）

1. **替换而非叠加**：当前 `lib/retriever.py` 的 `rewrite_query`（子问题+关键词拼接式扩展）对本知识库实测收益不明确，意图化改写上线后建议直接替换，避免双重改写稀释关键词。
2. **history 来源**：`frontend/app.py` 的 `sess_get(session_id)[-6:]` 即最近 3 轮，可直接格式化为 `{history}` 文本传入 Step 1。
3. **降级策略**：Step 1 调用失败或 `confidence < 0.6` → 跳过改写，用原 query 走现有检索链路（保证可用性兜底）。
4. **评估口径**：多意图拆分后检索应逐子问题合并去重候选集，再统一 rerank，避免子问题互相挤占 top_k。
5. **追问计数**：同一 session 连续追问不超过 2 次，第 3 次无论信息是否齐全都按默认值强行作答，防止追问死循环。
