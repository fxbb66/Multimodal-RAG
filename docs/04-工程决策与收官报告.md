### 13.3 向量生成与存储逻辑

- **视觉向量**：图片 → data_url → DashScope 风格 `input.contents[{image}]`（契约与既有文本块同模型同空间，1152 维）✅
- **文本向量**：`f"{cap}\n{ocr}"` → 同模型 text 嵌入 → 与 BM25 文本同源，向量空间一致 ✅
- **存储**：两行同组、L2 归一化后入 IndexFlatIP；维度强校验保留；`chunk_hash":vt"` 后缀保住唯一性检查 ✅
- **观测点 1（静默降级）**：`embed_image` 文本向量失败时回退 `text_vec=visual`（影子=视觉副本，归并后退化为旧单向量行为——降级本身优雅），但**只 print 不计数**：哪几张回退、双向量实际覆盖率多少，build_report 无记录——违反项目自己的"降级必须可观测"原则（rerank 熔断都记了 fallbacks/circuit_skips）。
- **观测点 2（BM25 全局轻迁）**：BM25 文档数 481→490（9 条空文档进 n 与 avgdl）→ 全文本块 idf 轻微上移（f=1 项约 +0.3%）、长文档 tf 归一化分母变小。RRF 按位次融合，影响仅限 BM25 top-20 内部换位，风险低；但**跨索引档位对比存在微小噪声**，归因时需知悉（新基线必须重标定，不能与旧读数直接比）。

### 14.1 先纠正问题框架：本项目根本不是 Agent

"要不要接 Agent 框架"隐含一个前提：本项目是（或应该是）Agent。这个前提不成立。

#### 14.1.1 三个判据逐项核对

| Agent 的定义性特征 | 本项目实际 | 结论 |
|---|---|---|
| **控制流由模型决定**（选择哪个工具、循环几轮、走哪条分支） | 拓扑写死：意图分类 → 向量化 → 混合召回 → rerank → MMR → 限额 → 生成。模型只做三个单点判断（意图七分类、改写、生成），**没有任何一步是模型决定"下一步做什么"** | ❌ |
| **工具集可被模型自由调用** | 唯一外部调用是 LLM API 与 rerank API，都是管道内固定环节，不是"可选工具" | ❌ |
| **存在自主循环**（观察 → 决策 → 再行动） | 单轮直达，无观察-再行动循环（`app.py:672-750`） | ❌ |

**本项目是 Prompt Chaining（工作流）+ Routing（意图路由）+ 会话记忆**——这在 2026 年的架构谱系里属于"确定性工作流"，不是 Agent 的低配版，而是**另一个物种**。

#### 14.1.2 为什么这不是缺陷，而是选择

行业共识已经很清楚：框架选型只决定约 20% 的成败，其余 80% 是 prompt 设计、工具质量、评估设施（多份 2026 年框架横评给出同一经验值）。本项目恰恰把 80% 做在了前面——135 条意图金标、183 对 QA 金标、19 档评估网格、chunk_hash 重映射、三级缓存指纹。

更关键的一条行业教训：**"五 Agent 系统处理一个没有工具边界、没有上下文边界、也不需要独立复核的任务，只是一个更慢更贵的单 Agent"**。本项目的任务是"从固定知识库回答一个客服问题"，既无工具边界也无独立复核需求——强行 Agent 化就是这句话描述的反例。

### 14.3 决策判据（本报告的核心交付）

#### 14.3.1 什么时候该用 Agent 框架 —— 五项判据

> **满足 ≥2 项** 才进入框架评估；满足 ≥3 项则框架明显优于手搓。

| # | 判据 | 具体表现 | 为什么框架能赢 |
|---|---|---|---|
| **A1** | **控制流不可预先枚举** | 分支/循环次数取决于模型输出；无法用 if-else 画完整个流程图 | 图式编排 + 运行时状态是框架的原生能力 |
| **A2** | **状态需跨请求存活 + 中断可恢复** | 任务跑几十分钟；进程重启要续跑；人工审批后从断点继续 | checkpointing 是 LangGraph/MAF 的核心卖点，自研成本高（状态序列化 + 版本迁移 + 回放） |
| **A3** | **多角色且上下文边界不同** | 不同 Agent 用不同 prompt/工具/模型，且互相不能看全量上下文 | 角色隔离与消息路由是 CrewAI/AutoGen 的原生抽象 |
| **A4** | **工具集动态发现** | 工具目录会变（MCP server 接入、插件市场），不能编译期枚举 | MCP 原生支持，自研要写协议层 |
| **A5** | **需要可审计的执行轨迹回放** | 合规要求"复现某次决策的完整链路"；金融/医疗/法务场景 | time-travel debugging + 结构化 trace 是框架强项 |

**反判据（出现即慎重）**：任务拓扑固定、指标已标定、依赖体积敏感、团队 ≤2 人。

#### 14.3.2 什么时候该手搓 —— 五项判据

> **满足 ≥2 项** 即应手搓；满足 ≥3 项应明确拒绝框架。

| # | 判据 | 具体表现 |
|---|---|---|
| **B1** | **拓扑固定，LLM 只做单点决策** | 分类 / 改写 / 生成，下一步动作由代码决定而非模型 |
| **B2** | **指标可量化且已标定** | 框架默认值（如 MMR 的相关性定义、RRF 的权重语义、BM25 的分词）会覆盖已标定参数 |
| **B3** | **需要跨 provider 的降级/熔断/预算控制** | 框架无对应件，且必须嵌进框架接口才能用（本项目 rerank 双协议降级链是典型） |
| **B4** | **依赖体积或启动延迟敏感** | 本地部署、离线、冷启动有 SLA（本项目实测引入 LangChain = +55 个包） |
| **B5** | **代码总量 < 1 万行且作者 ≤2 人** | 复杂度尚在单人可完全掌握的范围内，框架的"降低认知负担"收益未到临界点 |

#### 14.3.3 本项目逐项打分

| 判据 | 本项目 | 判定 |
|---|---|---|
| A1 控制流不可枚举 | 拓扑完全固定 | ❌ |
| A2 状态跨请求 + 中断恢复 | 会话 LRU + TTL，2 小时过期即丢，**无跨重启需求** | ❌ |
| A3 多角色上下文隔离 | 单角色（客服助手） | ❌ |
| A4 工具集动态发现 | 零外部工具 | ❌ |
| A5 执行轨迹回放 | 有 `trace` 字段但**无合规硬要求**，且现有 trace 已够用 | ⚠️ 部分 |
| **Agent 判据合计** | | **0.5 / 5** |

| 判据 | 本项目 | 判定 |
|---|---|---|
| B1 拓扑固定 | 是 | ✅ |
| B2 指标已标定 | 19 档网格 + 135/183 金标，每个超参都有标定产物 | ✅ |
| B3 降级/熔断/预算 | rerank 双协议降级链 + 600s 熔断 + 意图 18s 总预算 | ✅ |
| B4 依赖/延迟敏感 | 11 个直接依赖全 pin | ✅ |
| B5 规模 | 6430 行，单作者 | ✅ |
| **手搓判据合计** | | **5 / 5** |

**结论：0.5 vs 5。这不是"可选可不选"，而是判据已经给出明确答案。**

### 14.4 如果一定要接：哪些框架在什么假设下成立

> 前提：先出现 §3.1 中 ≥2 项。以下为假设场景下的排序，不是建议。

#### 14.4.1 假设场景 → 框架映射

| 假设的新需求 | 推荐 | 理由 | 预估成本 |
|---|---|---|---|
| 加 1-2 个实时查询工具（票务余量、排队时长） | **不引框架**，OpenAI SDK function calling | 单 Agent + 少量工具是 vendor SDK 的甜区（约 80 行） | 1-2 人日 |
| 加 5+ 工具 + 人工审批 + 长任务（例：自动生成周报并等审批发布） | **LangGraph** | A1+A2+A5 同时命中，checkpoint 与 HITL 是刚需 | 5-8 人日 |
| 多角色内容生产（营销文案 / FAQ / 质检三方互评） | **CrewAI** | A3 命中，30-60 行起原型 | 2-3 人日 |
| 结构化抽取（票务政策表 → JSON schema） | **Pydantic AI** | 类型安全，避免"返回垃圾但不报错" | 1-2 人日（也可直接用 pydantic + OpenAI 的 response_format，约 40 行） |
| .NET / Azure 深度绑定团队 | **Microsoft Agent Framework** | 生态一致，1.0 已 GA | 需重写 |
| 知识库规模扩到 10 万+ chunk、需多路召回编排 | **LlamaIndex / Haystack** | 检索管线强项 | **不推荐**：与现有结构感知切片冲突（见 4.3） |

#### 14.4.2 LangGraph 的单独说明（唯一值得留观察位的）

在 Agent 框架里，LangGraph 是唯一在本项目语境下可能产生真实价值的：

- **真实的不可替代点**：`checkpointer`（状态持久化 + 崩溃恢复 + 从任意节点重放）。自研等价物需要状态序列化 + 版本迁移 + 幂等重放，约 300-500 行且容易出错。
- **不成立的点**：本项目当前没有跨请求存活的任务。会话 2 小时过期本身就是设计决策（`SESSION_TTL=7200`），不是缺陷。
- **结论**：留观察位，不引入。触发条件见 §6。

#### 14.4.3 为什么检索类框架（LlamaIndex）不适合本项目

它与本项目冲突的不是能力，而是**分层顺序**：

```
本项目：结构感知切片（表格整块/父子块/OCR 页） → FAISS+BM25 索引 → 混合检索 → rerank
LlamaIndex：NodeParser（按长度/语义切） → VectorStoreIndex → retriever → postprocessor
```

LlamaIndex 的 `NodeParser` 无法表达"表格整块不切分""PPT 备注与正文合并""扫描页 OCR 结果挂到父块"这些规则——`1-parse_and_chunk.py` 1289 行里约 60% 是这类格式特化逻辑。引入框架等于把最费力的部分作废，然后重写成框架的 node 模型。

**判断：检索层一旦自研到"结构感知"这一步，就已经越过了框架能覆盖的边界。**

### 14.5 框架能力 vs 手搓成本对照（这决定 80% 的判断）

| 能力 | 框架版 | 手搓版 | 手搓性价比 |
|---|---|---|---|
| 单 Agent + 1-2 工具 | OpenAI Agents SDK ~20 行 | function calling 循环 ~80 行 | ⚠️ 框架略优，但不值得为 60 行引入依赖 |
| 会话持久化（跨重启） | LangGraph checkpointer | SQLite + JSON 序列化 ~30 行 | ✅ 手搓胜（无跨重启需求） |
| 证据充分性自检 + 一次重检索 | 无直接对应件 | `while` + 自检 prompt ~15 行 | ✅ 手搓胜 |
| 多级降级 + 熔断 | 无对应件 | 现有 75 行（`retriever.py:211-286`） | ✅ 手搓唯一解 |
| 人工审批（HITL） | LangGraph interrupt ~20 行 | Flask 路由 + 状态机 ~50 行 | ⚠️ 框架略优 |
| 执行轨迹回放 | time-travel debugging | 现有 `trace` dict + 日志 | ⚠️ 取决于合规要求 |
| 多 Agent 角色协作 | CrewAI ~40 行 | 自研消息总线 ~200-300 行 | ✅ 框架明显优（本项目无此需求） |
| 工具动态发现（MCP） | 原生支持 | 手写 MCP 客户端 ~150 行 | ✅ 框架明显优（本项目无此需求） |

**读法**：8 项能力里，框架明显占优的只有 2 项（多 Agent 协作、MCP 动态发现），而这两项本项目都不需要。其余 6 项手搓成本均 ≤ 80 行或已有实现。

**这是"手搓"最关键的经验值：Agent 框架约 80% 的价值集中在 100-300 行可复刻的范围内，剩下 20%（多 Agent 协作 + checkpoint 恢复）才是真正不可替代的——而那 20% 恰好对应 A2/A3/A4 三条判据。**

### 14.6 本项目的行动方案

#### 14.6.1 当前决策（明确不做的事）

- ❌ 不引入 LangChain / LangGraph / CrewAI / MAF / Pydantic AI 中任何一个
- ❌ 不为"架构显得先进"做 Agent 化改造
- ✅ 继续保持"确定性工作流 + 单点 LLM 决策"，并把这条写进架构说明（这是加分项，见 §7）

#### 14.6.2 若要做"Agentic"能力的正确顺序（不引框架也能做）

按投入产出排序，前三项都不需要框架：

| 优先级 | 能力 | 实现方式 | 预估 | 预期收益 |
|---|---|---|---|---|
| **P0** | 证据充分性自检 + 一次重检索闭环 | 生成前加一道"上下文是否足以回答"判定，不足则用改写后的 query 重检索一次（`max_retry=2`）。**复用 rerank 熔断的降级模式** | 1-2 人日 | 直接改善"证据覆盖 0.650 / 证据到位命中 0.808"之间的缺口——这是当前最大的量化瓶颈 |
| **P1** | 183 金标全量复跑 | 调 `ANSWER_EVAL_N` + 重跑 `4-evaluate.py` | 0.5 人日 | 所有后续决策的共同尺子（上一轮已列为 P0 阻塞项） |
| **P2** | 会话持久化（仅当有跨重启需求） | SQLite + 现有 dict 结构序列化 | 0.5 人日 | 补上唯一的"框架真实优势"缺口，成本 30 行 |
| **P3** | 工具调用（仅当有实时数据需求） | OpenAI SDK function calling 循环 | 1-2 人日 | 新增能力（票务余量/排队时长） |
| **P4** | LangGraph 评估 | 仅当 A1+A2+A5 同时命中 | 5-8 人日 | 到这一步才值得谈框架 |

**注意 P0 的性质**：它会让系统呈现"一次自检 + 一次重检索"的循环，**看起来像 Agent，但拓扑仍然固定**（循环次数上限写死为 2）。这是"用工作流实现 Agentic 效果"的标准做法，不需要任何框架。

#### 14.6.3 迁移触发条件（唯一需要重新评估的时刻）

**以下三条同时成立时，才启动 LangGraph 评估：**

1. 出现 ≥3 个外部工具（票务 API、排队时长、天气、订单查询…）
2. 需要人工审批环节（如自动生成对外回复并等人工确认）
3. 任务需要跨请求存活（分钟级以上长任务，或进程重启后续跑）

**任一不成立 → 继续手搓。**

历史教训支撑这条保守线：选框架的团队在 12 个月内已经历 LangChain 拆包（2025-10）与 AutoGen/SK 合并（2026-04）两次强制迁移。

### 14.7 对外表述建议（面试/评审场景）

这个项目是作品集性质，因此"为什么不用框架"的表述质量本身就是评估项。三种说法，效果差异很大：

| 说法 | 评价 |
|---|---|
| ❌ "没用框架，因为项目比较小" | 减分。暗示能力边界，且事实不符（6430 行、三层评估体系） |
| ⚠️ "考虑过，但觉得手写更可控" | 中性。没有证据，听起来像个人偏好 |
| ✅ "评估过，用五项判据否掉了" | 加分。附三个具体技术点即可闭环 |

**推荐表述（可直接用）**：

> 我用五项判据判断该不该上 Agent 框架：控制流是否不可枚举、状态是否需跨请求存活、是否多角色、工具集是否动态、是否需要轨迹回放。这个项目 0 项命中，手搓判据 5 项全中，所以是确定性工作流而非 Agent。
>
> 结论不是拍脑袋的，三条硬证据：
> ① LangChain 1.x 把全部 Retrievers 移进 legacy 包，接入实测新增 55 个传递依赖；
> ② 框架的 MMR 用查询余弦做相关性，而我实测这条路线会让 recall 从 0.951 掉到 0.407，我用位次相关性才修回来——框架默认值会覆盖我标定过的参数；
> ③ 真正不可替代的框架能力只有两个：多 Agent 协作和 checkpoint 恢复，而我的场景都不需要，其余 80% 的价值我 100 行以内能复刻。
>
> 我保留了一个观察位：如果未来出现 3 个以上外部工具 + 人工审批 + 长任务同时成立，我会评估 LangGraph，因为 checkpoint 自研成本太高。

| 问题 | 结论 | 一句话依据 |

| 是否值得用 LangChain 重写检索链路？ | **不值得** | LangChain 能覆盖的只有 RRF 融合与 chat 调用两块；其余 7 项关键机制无对应件，替换即降级 |

### 15.2 LangChain 1.x 的现实形态（2026-10 事实核查）

这一节决定整个评估的性质。**若按 2024 年的认知评估，结论会完全相反。**

#### 15.2.1 包结构已被官方重构

LangChain 1.0 于 2025-10-22 发布，做了一次架构级拆分：

| 包 | 职责 | 本项目是否需要 |
|---|---|---|
| `langchain` (1.4.6) | 只剩 `create_agent` / `init_chat_model` / messages / tools | **不需要**（无 Agent） |
| `langchain-core` (1.6.12) | Runnable、LCEL、消息抽象 | 可有可无 |
| `langchain-classic` (1.0.8) | **Legacy 兼容包**：旧 chains、**全部 Retrievers**、indexing API、hub | 官方标注 legacy |
| `langchain-community` (0.4.2) | 文档加载器、冷门集成大杂烩（含 `BM25Retriever`） | 仅 loader 有价值 |
| `langgraph` (1.2.16) | Agent 图式编排 | 当前不需要 |
| `langsmith` (0.14.11) | 可观测平台 SDK（联网上报） | **合规不可用** |

官方 migration guide 原文归类：*Retrievers (e.g. MultiQueryRetriever or anything from the previous `langchain.retrievers` module) → `langchain-classic`*。

**这意味着**：想用 LangChain 做「混合检索 + rerank」这件事，在 1.x 时代必须装 `langchain-classic`——一个官方定义为"给老项目迁移用、新项目禁用"的包。

### 15.4 三个致命不兼容点（可量化的否决理由）

#### 15.4.1 MMR 的相关性信号方向相反 —— 最硬的一条

本项目 MMR 实现（`retriever.py:1142-1169`）的设计注释直接写明：

> 旧实现用原始余弦做相关性，会把 rerank 排序整体丢弃——新空间下纯向量信号弱（诊断实测：**MMR-only recall@5 0.884→0.407**），调 λ 无法补救。

修复方案是「相关性项用池内位次，多样性项用向量余弦」，修复后 `recall@5 = 0.951 / MRR = 0.771`（`output/diag_mmr_fix.json` F1 档）。

LangChain 的 `max_marginal_relevance_search` 正是"相关性 = 查询-文档余弦"的实现。**它的默认行为等于本项目的旧实现**，也就是被实测否决的那一版。接入后只有两条路：

- 沿用框架默认 → 预期 recall 下滑 30~50pt（按实测退化幅度）
- 写自定义 MMR 传进去 → 框架层零收益，反而多一层适配

这条单独就足以否决"用 LangChain 替换检索层"。

#### 15.4.2 中文 BM25 的分词默认值不成立

`langchain_community.retrievers.BM25Retriever` 默认 `preprocess_func` 为按空白切分。中文无空格，整句退化为单 token，`score()` 的 TF/IDF 全部失真。

现有实现用字符二元组（`char_ngrams`, `retriever.py:71-75`），零依赖、对中文短查询友好、已随 183 金标标定。替换路径只能是：

```python
BM25Retriever.from_documents(docs, preprocess_func=lambda t: [t[i:i+2] for i in range(len(t)-1)])
```

—— 也就是**把现有实现原样搬过去**，额外换来 `rank_bm25` 依赖和一层 Retriever 封装。

#### 15.4.3 rerank 降级链无框架对应件

现有降级链包含三层非标准语义（`retriever.py:237-286`）：

1. **双协议**：AGICTO 走 Cohere 风格 REST `/v1/rerank`；百炼走 `dashscope.TextReRank` 原生 SDK。信封字段完全不同。
2. **确定性失败判定**：`HTTP 200 + {"message": "Please add payment method..."}` 视为失败并熔断——这是 2026-10-01 AGICTO 欠费事故的直接产物，每查询曾白等约 6s。
3. **600s 熔断 + 充值后自动探测恢复**：`_CIRCUIT` / `_CIRCUIT_TTL`，欠费期不让用户为死模型付 RTT。

LangChain 的 `ContextualCompressionRetriever` 只定义"压缩/重排"接口，上述三层全部要自写 `BaseDocumentCompressor` 子类。**改写后的代码量 ≥ 现有代码量**，且失去 `RERANK_STATS`（calls/fallbacks/circuit_skips）这套已接入 `/api/health` 与评估结论的可观测指标。

### 15.7 决策结论

#### 15.7.1 主结论

**不接入 LangChain 本体。**

理由收敛为一句：**这个项目的核心竞争力恰恰是"框架默认值被实测指标替换掉"的那些部分**——位次 MMR、字符 BM25、双协议 rerank 降级链、确定性意图规则门。把这些交给框架，等于把已经标定过的旋钮换回默认值，然后用 8-12 人日证明指标变差。

#### 15.7.2 三条条件性窄路径（唯一值得做的方向）

| 路径 | 做什么 | 值得条件 | 预估工期 | 生产影响 |
|---|---|---|---|---|
| **M1 生成侧包装** | 用 `langchain-openai` 的 `ChatOpenAI.astream` 替换 20 行生成调用 | 仅当需要 LangGraph/LangSmith 生态对接 | 1-2 人日 | 可 feature flag 回滚 |
| **M2 评估侧隔离** | 独立 `requirements-eval.txt` venv 引入 RAGAS，补 3 个生成侧指标 | 需要"幻觉率/答案相关性"这类第三方口径做交叉验证 | 3-5 人日 | **零**（不进生产） |
| **M3 Agent 化** | 单独评估 LangGraph（不装 langchain 主包） | 出现 ≥3 个外部工具编排需求（票务 API / 实时排队 / 天气） | 5-8 人日 | 新增能力，非替换 |

**M0（前置，0.5 人日）**：只装 `langchain-core`，把 `HybridRetriever.search` 包成 `BaseRetriever` 子类，跑通"框架 → 现有检索"的单向调用。**目的仅为验证生态兼容性，不改任何生产路径。** 若此步就出现 numpy/pydantic 冲突，M1-M3 全部终止。

#### 15.9.2 M0 实施细节（0.5 人日）

```python
# lib/lc_adapter.py（新增文件，不修改现有任何文件）
from typing import Any, Callable
from langchain_core.retrievers import BaseRetriever
from langchain_core.documents import Document


class DisneyRetrieverAdapter(BaseRetriever):
    """单向适配：只把现有 HybridRetriever 暴露给 LangChain 生态，不改内部逻辑。

    retriever : 现有 HybridRetriever 实例（复用其 search / meta，不做任何改动）
    embed_fn  : 查询向量化函数，由调用方注入（复用 app.py 的 get_text_embedding，
                含 LRU 缓存与 AGICTO 错误信封处理），适配器内不重复实现 embedding 调用
    """
    retriever: Any
    embed_fn: Callable[[str], Any]
    k: int = 5

    def _get_relevant_documents(self, query, *, run_manager=None):
        vec = self.embed_fn(query)
        ranked = self.retriever.search(vec, query, k=self.k, use_mmr=True,
                                       mmr_lambda=0.72, max_per_source=3)
        return [Document(page_content=self.retriever.meta[i]["content"],
                         metadata={"chunk_hash": self.retriever.meta[i].get("chunk_hash"),
                                   "source": self.retriever.meta[i].get("source"),
                                   "score": float(s)})
                for i, s in ranked]
```

注意：`BaseRetriever` 是 pydantic 模型，字段必须以类属性声明（如上），不能写在 `__init__` 里；`embed_fn` 注入而非内部新建客户端，是为了不绕过现有 embedding 缓存与错误提示链路。

**验收**：`DisneyRetrieverAdapter.invoke(q)` 与 `HybridRetriever.search()` 返回的 chunk_hash 序列**逐位一致**（同一 query，k=5）。不一致即适配层有语义损耗，停止推进。

### 15.11 一句话总结（可直接用于对外表述）

> **评估过，结论是不接。** LangChain 1.x 已把检索组件整体移入 legacy 包 `langchain-classic`，主包只剩 Agent 构建；而本项目真正吃分的是框架没有的几件事——字符二元组中文 BM25、位次版 MMR（框架默认的余弦 MMR 在本项目实测会让 recall 从 0.951 掉到 0.407）、带熔断的双协议 rerank 降级链、能压到 1.06% 真实降级率的意图规则门。接入的实际收益是少写 20 行生成代码，成本是 55 个新增依赖 + 8-12 人日重写 + 指标下滑风险。
>
> 唯一值得做的是把 RAGAS 关进独立 venv 补三个生成侧指标（幻觉率/答案相关性/上下文精度），因为它能提供现有口径没有的第三方视角，而这条路径对生产零影响。
>
> **2026-10-22 补充（附录 B 四项关账后）**：RAGAS 这条窄路径已实际执行（隔离 venv 97 包 + 三指标 50/183 题），结果为**否定性**——三组 Spearman 交叉验证全部未达 0.7 门槛且为负相关（-0.089 / -0.041 / -0.145），按既定验收条款不予采信；M0/M1 均判定不做（dry-run 证明兼容成本仅 12 包，但无下游消费者）。**六条决策触发器逐条复查，0 条成立**。净效果：主结论不变，且"唯一值得做的那一条"已被证伪一次，LangChain 方向在本项目上**已彻底关闭**，除非未来真的出现工具编排或生态对接需求（届时按 §15.9.3 的 `GEN_BACKEND` 开关方案施工）。
